## 4. 允许重新构建的条件

在修改依赖前不得直接覆盖固定候选包。必须按以下顺序操作：

1. 备份源码、当前候选 WAR、外置驱动和五库验证配置。
2. 使用独立临时工作树隔离安全修复，保留 `9cb0e00102887837719200b12aabd27e1bc794b1` 作为可回退基线；未经用户要求不创建新分支或提交。
3. 先升级已获取到的 Jackson 和 MySQL Connector/J；Spring Security 单独核实补丁来源，确认 Maven 依赖收敛后再构建。

5. 对新 WAR 重新执行完整性审计，确认 REST/UI 的 Flowable 模块和应用类没有遗漏。
6. 重新执行 MySQL、PostgreSQL、Oracle、达梦、金仓五库回归，以及 LDAP、UI 登录、模型发布、任务办理、动态传人、抄送、历史、导出和回调测试。

## 5. 不允许的做法

- 不把源码测试通过当成 WAR 运行时安全通过。
- 不把 44 条公告全部标为“不适用”。
- 不把 `8.0.33` 的源码 POM 版本当成外置 `drivers/mysql.jar` 的实际版本。

- 不在没有驱动授权和回滚备份的情况下对外分发国产数据库驱动。

## 9. 同摘要 WAR 的 Spring 运行配置核查

继续使用第 8 节 WAR，未重编译产品。探针加载 WAR 内原始类及依赖，在隔离 H2 库、随机本机端口下分别运行 REST/UI 的本地认证与测试 LDAP 四种组合；不连接业务数据库、不改 LDAP 密码。这是配置和类行为核查，不替代 WarLauncher 部署或实际业务页面验收。

经容器加载全部延迟 Servlet 后，REST 为 10 个 Spring 上下文、443 条控制器映射；UI 为 13 个上下文、733 条映射。映射数量不是全局去重 URL 数量。以下检查均已覆盖四种组合：

- 未启用 X.509，RequestCache 为 NullRequestCache；所有安全响应头过滤器启用提前写入。

38 条唯一公告现已逐项记录为：3 条应用层缓解已有证据、11 条仅在受测配置下缺少触发前提、7 条可选消息功能尚未专项验证、1 条生产部署条件不明确、16 条仍需继续分析。以上不是在线复扫，也不是将公告删除或统一判为不适用。

### 9.1 Multipart 阻断保留

[Spring 官方 CVE-2026-41853](https://spring.io/security/cve-2026-41853) 明确列出三项前提：MVC/WebFlux、接收 Multipart、前置 WAF/代理解析并检查 Multipart 内容。本 WAR 确实使用 StandardServletMultipartResolver 和 PutAwareStandardServletMultiPartResolver，前两项成立。

用户反馈生产是否存在此类 WAF/代理“暂时不确定”，因此此项继续保留发布阻断。直连成功不证明代理解析一致；不能以关闭 WAF 或删掉上传能力替代修复。下一步需基于兼容补丁和最终代理链验证，不能擅自填写“不受影响”。

### 9.2 密码配置和反序列化边界

探针确认默认本地密码编码是 NoOpPasswordEncoder，不能因为代码包含 BCrypt 加固就宣称默认密码安全。新建本地用户库可选择如下配置，再完成登录、创建用户和改密验收：

```properties
flowable.idm.password-encoder=spring_delegating
```

**已有用户库不得直接切换。** 旧明文、裸 BCrypt 或带算法前缀的密码需要分别制定迁移方案，否则会影响现有登录；LDAP 密码仍由目录服务处理。本轮没有更改任何环境的编码配置。

源码还存在默认允许 Java 序列化变量的 `rest.variables.allow.serializable` 入口。这不是“无 HttpInvoker 即安全”可以排除的问题，需继续核对 go-common JSON/二进制变量契约；本轮未贸然禁用，以免破坏既有功能。

## 10. REST Java 对象上传默认关闭及兼容验证

在第 8 节临时源码上完成两个 WAR 的默认配置加固：

```properties
rest.variables.allow.serializable=false
```

REST WAR 原来默认 `true`，UI WAR 原来未配置而由资源类回退到 `true`；现在两者随包配置都显式为 `false`。嵌入式 REST 库自身的回退值未改。外部 properties、环境变量或启动参数仍可覆盖随包默认值，部署时须检查最终生效配置，不能只看 WAR 文件。

### 10.1 影响范围与开发接入

- 拒绝 Multipart 请求中的 `type=serializable` Java 对象流上传，包括新增和更新；覆盖 BPMN 流程实例、执行实例、任务，以及 CMMN 案例、计划项、任务六类变量入口。受测默认配置返回 HTTP `415`，新增不写入，更新保留原值。
- 保留普通 `binary` 变量、未指定类型的文件上传、任务附件和 BPMN/CMMN 部署上传。不是禁用 Multipart，也没有解决第 9.1 节 WAF/代理解析差异公告。
- go-common `toFlowableVariables` 使用 JSON `{name,value}`，不发送顶层 `type=serializable`。`nextAssignee`、`nextCandidateUsers`、`nextCandidateGroups` 和抄送变量无需改成 Java 对象流，也不需要为此开启兼容开关。
- JSON 数组/对象可能仍由引擎内部 Serializable 类型持久化。因此没有删除引擎的序列化类型，也没有改变历史变量读取。**此开关不是全引擎反序列化沙箱，不能据此宣布反序列化风险全面消除。**

现有系统若确实依赖 Java 对象上传，只能在安全评估并限制调用方后显式配置 `rest.variables.allow.serializable=true`；本轮验证了该旧行为仍可启用，但这会重新打开对象反序列化入口，不是推荐部署方案。仅为了 JSON、动态传人或附件而设置 `true` 是不必要的。
