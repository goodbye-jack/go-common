# 工作流平台接入总说明

## 1. 文档定位

当前 `go-common/workflow` 对外只保留 3 份正式工作流文档：

1. `工作流平台接入总说明.md`
   - 面向后端、前端、测试、实施
   - 负责说明架构、配置、标准接口、调用顺序、字段语义
2. `工作流BPMN建模与变量规范.md`
   - 面向流程设计人员、平台架构人员
   - 负责说明 BPMN 如何建模、变量如何命名、哪些写法允许、哪些写法禁止
3. `Flowable UI与REST本地启动说明.md`
   - 面向本地联调和环境运维人员
   - 负责说明 UI/REST/数据库如何启动、如何验证、如何切换 LDAP

除这 3 份外，其余旧的工作流说明、发布通知、版本说明、模板类文档都不再作为正式接入依据。

另外保留 1 份补充型回归文档：

- `go-common-v1.3.8-工作流发版回归清单.md`
  - 只用于发版前回归、联调前核对、测试留痕
  - 不是正式接入主说明，不替代上述 3 份文档

### 1.1 本文适合谁看

- 后端开发
- 前端开发
- 测试人员
- 实施人员
- 需要统筹工作流接入方案的架构人员

### 1.2 本文解决什么问题

本文是工作流接入主入口，重点回答下面这些问题：

- `flowable-ui`、`flowable-rest`、业务系统三者职责怎么划分
- 业务系统 `config.yaml` 应该怎么配
- 业务代码里怎么注册 go-common 工作流接口
- 前端应该按什么顺序调用接口
- 各标准接口分别干什么、什么时候用
- `/api/v1/workflow/callback` 应该怎么理解和使用

本文不负责展开说明：

- Flowable 容器、MySQL、LDAP 的部署启动细节
- BPMN 每一种节点的建模细节

这些内容分别去看：

- 部署启动：`Flowable UI与REST本地启动说明.md`
- BPMN 规范：`工作流BPMN建模与变量规范.md`

### 1.3 建议阅读顺序

第一次完整接入建议按照下面顺序阅读：

1. `Flowable UI与REST本地启动说明.md`
2. `工作流BPMN建模与变量规范.md`
3. `工作流平台接入总说明.md`

如果你不是做首次接入，而是在准备发布 `go-common` 新版工作流能力，读完这 3 份主文档后，再补看：

4. `go-common-v1.3.8-工作流发版回归清单.md`

### 1.4 3 分钟速读

如果你现在只想先知道“业务系统到底应该怎么接、前后端先跑哪条最小链路”，先记下面 8 条：

1. 业务系统最小配置先只关注：
   - `workflow.flowable.*`
   - `workflow.callback.*`
2. 发起流程必须拆成两步：
   - 先保存业务数据
   - 再调用 `POST /api/v1/workflow/process/start`
3. `claim / unclaim / delegate / resolve / transfer`
   - 只改“谁来办”
4. `complete`
   - 只改“流程往哪走”
5. 我的待办看 `todo`，我的已办看 `done`，我的动作记录看 `task-records`。
6. 页面上的“流程步骤主链路”优先看 `progress-timeline`，不要直接拿 `progress-view.steps[]` 或 `action-timeline` 顶上去。
7. callback 不是只注册路由就会自动生效：
   - 启动流程时还要显式传 `callbackUrl / callbackEvents`
8. 标准 callback 接收成功，不等于业务主表状态自动更新：
   - 如果项目要更新业务状态、写业务日志、发通知，还要补业务系统自己的 callback 扩展处理

## 2. 先说结论

业务系统接入工作流时，只需要记住下面 8 条：

1. 业务数据必须落自己的业务表，不能指望 Flowable 表单代替业务存储。
2. 发起流程必须分两步：
   - 先调业务保存接口
   - 再调工作流启动接口
3. `claim / unclaim / delegate / resolve / transfer` 只负责“谁来办”。
4. `complete` 只负责“流程往哪走”。
5. 退回、重审、驳回、补正必须通过 BPMN 网关和变量表达，不新增“任意跳转”接口。
6. BPMN 中不要直接写业务私有变量如 `${bizSpecificApproverId}` 作为长期平台契约，统一用标准变量。
7. 流程轨迹现在分四类：
   - `progress-view` 看流程摘要、BPMN 结构、当前节点总览
   - `progress-timeline` 看真正走过或当前正在处理的主链路步骤
   - `task-records` 看每个步骤下发生过哪些办理动作
   - `action-timeline` 只看办理权动作审计，不建议直接拿来做主进度页
8. “我的已办”和“我的办理记录”不是一回事：
   - `done` 只看真正完成过的任务
   - `task-records` 看认领、委派、转办、完成等实际办理动作

当前公司级标准主路线固定为：

1. `flowable-ui`
   - 负责流程图、表单模型、部署发布、身份源接入与节点人/组配置
2. `flowable-rest`
   - 负责流程运行时接口，供业务系统通过 `go-common` 调用
3. `LDAP`
   - 负责用户、组、角色、岗位等身份数据
4. 业务系统
   - 负责业务数据、业务状态、业务详情、业务表单提交、LDAP 关系同步
5. `go-common/workflow`
   - 负责标准工作流 API、callback、progress、timeline、task-records、form-ref 输出

默认不再把下面这条路线作为新项目推荐方案：

- 业务系统运行时自己查 LDAP，再通过 `nextAssignee / nextCandidateUsers / nextCandidateGroups` 临时算审批人

这条路线当前代码中仍有兼容能力，但已经降级为历史兼容模式。

## 2.1 5 分钟接入清单

如果你是第一次接入，不要一上来就翻所有接口。按下面顺序做，基本不会走偏。

### 第 1 步：先把平台启动起来

你至少要有下面两类服务：

1. `flowable-ui`
   - 给流程设计人员画流程图、发布流程
2. `flowable-rest`
   - 给业务系统运行时调用

还要有下面两类平台依赖：

3. Flowable 平台数据库
   - 给 `flowable-ui + flowable-rest` 提供流程、历史、表单、部署、身份元数据存储
4. Flowable 平台 LDAP
   - 给 Flowable 平台提供用户、组、角色来源

这里要特别区分两件事：

- Flowable 平台自己的数据库、LDAP，属于平台侧配置
- 业务系统自己的 `config.yaml` 只需要知道如何调用 `flowable-rest`

如果本地还没部署，先看：

- `Flowable UI与REST本地启动说明.md`

验收标准：

- 能打开 `flowable-ui`
- 能登录 `flowable-ui`
- 能在 `flowable-ui` 发布流程
- `flowable-rest` 的 `/service/management/engine` 可以返回结果

### 第 2 步：先把流程图画对

在 `flowable-ui` 里完成下面事情：

1. 创建 BPMN 流程
2. 配置用户任务
3. 配置候选人 / 候选组 / 固定办理人
4. 发布流程定义
5. 记住流程定义 `key`

如果你不确定节点到底该怎么配，先看：

- `工作流BPMN建模与变量规范.md`

当前标准主路线优先级如下：

1. `candidateGroups`
2. `candidateUsers`
3. `assignee`

也就是说：

- 新项目优先用 Flowable UI 里可见的用户/组配置能力
- 优先让 Flowable 平台结合 LDAP 解决“谁能处理”
- 如果使用 `candidateGroups`，公司标准建议只使用流程角色组编码，例如 `wfgrp:<tenantCode>:<groupCode>`
- 不建议再把部门组、岗位组暴露为 Flowable 可选组
- 不再把 `${bizSpecificApproverId}`、`${bizSpecificOwnerUserId}` 这类业务私有变量作为长期平台契约

验收标准：

- 流程已经发布，不是草稿
- 你知道自己要调用的 `processDefinitionKey`
- 节点办理人配置符合 Flowable 标准写法

### 第 3 步：业务系统补 `config.yaml`

业务系统至少补齐下面这些配置：

```yaml
workflow:
  api:
    enabled: true
    prefix: "/api/v1/workflow"
    sso_enabled: true
  callback:
    path: "/api/v1/workflow/callback"
    secret: ""
    public_base_url: "http://127.0.0.1:9080"
  flowable:
    base_url: "http://127.0.0.1:8087/flowable-rest/service"
    username: "rest-admin"
    password: "PLEASE_CHANGE"
```

第一次接入时，这 2 组配置最容易混淆，这里先直接说明：

- `workflow.flowable.*`
  - 是业务系统调用 Flowable REST 的运行时配置
- `workflow.api.*`
  - 是 go-common 在业务系统里暴露标准工作流接口时使用的配置

当前公司标准主路线下，默认不要求业务系统一上来就配置：

- `workflow.assignment.*`
- `workflow.identity.*`
- `workflow.formref.db_instance`
- `workflow.records.db_instance`

`workflow.directory.*` 要单独理解：

- 如果业务系统只需要“调用 Flowable REST 跑流程”
  - 那它不是最小接入前置项
- 如果业务系统还要通过 go-common 对外提供：
  - `/api/v1/workflow/me`
  - `/api/v1/workflow/me/manager`
  - `/api/v1/workflow/me/department`
  - `/api/v1/workflow/org/**`
  - 这类目录接口
  - 那就应按需配置 `workflow.directory.*`

这些配置要么属于：

- 历史兼容路线
- 可选增强能力

不是新项目最小接入前置条件。

尤其要注意：

- `workflow.callback.path`
  - 只决定“业务系统把 callback 路由暴露在哪个路径”
- `workflow.callback.public_base_url`
  - 只决定“Flowable 从外部访问业务系统时使用哪个宿主地址”
- `variables.callbackUrl`
  - 才决定“Flowable 运行时到底回调哪个完整地址”

也就是说：

- 配了 `workflow.callback.path`
  - 只代表业务系统路由准备好了
- 配了 `workflow.callback.public_base_url`
  - 才有条件拼出完整 callback 地址
- 还必须在启动流程时传 `callbackUrl` 和 `callbackEvents`
  - Flowable 才会真的发回调

开发第一次接入时，下面 5 组概念最容易混掉：

1. `workflow.flowable.base_url` 和 `workflow.callback.public_base_url`
   - 前者是“业务系统调用 Flowable REST 的地址”
   - 后者是“Flowable 反过来回调业务系统时访问的地址”
   - 这两个地址经常不是同一个宿主，尤其是“远端 Flowable + 本地业务系统 FRP 联调”场景
2. `workflow.callback.path` 和 `variables.callbackUrl`
   - 前者只是业务系统本地暴露的路由路径
   - 后者才是启动流程时真正告诉 Flowable 的完整回调地址
3. Flowable UI 登录地址 和 `workflow.flowable.base_url`
   - UI 地址是给人登录、建模、发布流程用的
   - `workflow.flowable.base_url` 必须指向 `/flowable-rest/service`
   - 不能把 UI 地址误填成 REST 地址
4. `workflow.formref.db_instance` 和 `workflow.records.db_instance`
   - 前者通常连 Flowable 元数据库，只服务于 `form-ref` 解析 fallback
   - 后者是 go-common 自己的 `workflow_task_records` 落库实例
   - 两者职责完全不同，不要因为名字里都带 `db_instance` 就混成同一种数据库
5. `db_instance` 和真实数据库名
   - `workflow.formref.db_instance: "flowable_meta"` 里的 `flowable_meta` 是“实例名引用”
   - `databases.mysql.flowable_meta.database: flowable_681_app` 里的 `flowable_681_app` 才是真实数据库名
   - 配错实例名时，常见表现是启动报错；配对了实例名但实例连错环境时，常见表现是运行期数据错乱

再补一句开发最容易配错的点：

- `password: "PLEASE_CHANGE"`
  - 只是文档占位示例，不是固定值
  - 如果你的本地 REST 账号是 `rest-admin/test`，这里就应改成 `test`
- `workflow.api.prefix`
  - 当前平台标准值就是 `/api/v1/workflow`
  - `v1.3.8` 起如果你不显式配置，默认也会按这个值注册
  - 如果老系统要继续保留旧前缀，必须在 `config.yaml` 里显式写出自己的旧值

如果需要完整字段解释，继续看本文第 5 章“推荐配置”。

验收标准：

- 业务系统已经知道 `flowable-rest` 地址、账号、密码
- 工作流接口前缀已经明确

### 第 4 步：业务后端注册工作流接口

这一步是最容易漏掉的。

只配 YAML 不会自动对外暴露工作流接口。你还必须在业务代码里注册：

```go
workflowapi.MustRegisterFromConfig(server)
```

推荐顺序：

```go
server := commonhttp.NewHTTPServer(serviceName)
registerBizRoutes(server)
workflowapi.MustRegisterFromConfig(server)
server.Prepare()
server.Run(addr)
```

完整说明看本文第 `5.3` 节“业务程序代码如何接入”。

验收标准：

- 启动日志里能看到 `WORKFLOW ROUTES REGISTERED`
- `/api/v1/workflow/...` 相关接口已经对外可访问

### 第 5 步：业务接口和流程接口分开

标准接入不是只做一个“万能 applications 接口”。

标准做法是拆成两步：

1. 先调业务保存接口
   - 保存自己的业务表
   - 生成 `bizId`
2. 再调工作流启动接口
   - `POST /api/v1/workflow/process/start`

验收标准：

- 业务保存失败时，不会误启动流程
- 流程启动失败时，可以明确知道问题在工作流侧
- `bizId` 与 `processInstanceId` 能建立映射关系

### 第 6 步：前端按标准接口接页面

前端最常用的页面，一般这样接：

- 发起页
  - 业务保存接口
  - `POST /api/v1/workflow/process/start`
- 我的待办
  - `GET /api/v1/workflow/me/tasks/todo`
- 我的已办
  - `GET /api/v1/workflow/me/tasks/done`
- 处理页
  - `GET /api/v1/workflow/tasks/{id}/context`
  - `GET /api/v1/workflow/tasks/{id}/form-ref`
  - `GET /api/v1/workflow/biz/{bizId}/progress-timeline`
  - `GET /api/v1/workflow/biz/{bizId}/task-records`
- 办理动作
  - `claim / unclaim / delegate / resolve / transfer / complete`

验收标准：

- 前端没有直接调用 `flowable-ui`
- 前端没有直接调用 `flowable-rest`
- 前端统一调用业务系统暴露出来的接口

### 第 7 步：最后联调整条链路

至少走完一次完整流程：

1. 登录业务系统
2. 保存业务
3. 启动流程
4. 查询待办
5. 打开处理页
6. 完成一次 `claim / complete` 或 `delegate / resolve / complete`
7. 查看进度时间线和办理记录
8. 验证业务状态是否同步更新

建议同时检查 callback 日志中是否已经能够直接看出：

- `bizId`
- `eventType`
- `processInstanceId`
- `taskId`
- `activityId`

如果这 8 步都通了，说明这套工作流接入已经具备可交付基础。

## 2.2 常见接入错误 Top 10

这一节不是补充阅读，而是高频踩坑清单。很多“接口不通”“待办不见了”“流程启动了但没人办”本质上都属于下面这些问题。

### 1. 只配了 `config.yaml`，没有在代码里注册工作流接口

典型表现：

- 项目启动成功了
- 但访问 `/api/v1/workflow/...` 全部 `404`
- 启动日志里没有 `WORKFLOW ROUTES REGISTERED`

根因：

- 你只写了 `workflow.*` 配置
- 但没有在代码里调用：

```go
workflowapi.MustRegisterFromConfig(server)
```

正确做法：

- 在业务路由注册完成后调用 `workflowapi.MustRegisterFromConfig(server)`
- 然后执行 `server.Prepare()`

### 2. 把 `flowable-ui` 当成运行时接口服务

典型表现：

- 前端或后端去调 `flowable-ui` 地址
- 明明流程图已经能打开，但流程接口就是不通

根因：

- `flowable-ui` 是设计平台，不是给业务系统跑运行态接口的

正确做法：

- `flowable-ui` 只负责画图、配图、发布
- `flowable-rest` 才是 go-common 调用的运行时服务
- 业务系统配置里 `workflow.flowable.base_url` 必须指向 `flowable-rest/service`

### 3. `flowable-rest` 地址配错了

典型表现：

- 启动流程时报 `404`
- 查询引擎信息时报认证弹窗或找不到路径

常见错法：

- 少写了 `/flowable-rest/service`
- 错把 `flowable-ui` 地址填进 `base_url`

正确示例：

```yaml
workflow:
  flowable:
    base_url: "http://127.0.0.1:8087/flowable-rest/service"
```

### 4. 前端直接调用 `flowable-rest`

典型表现：

- 页面里直接写死 Flowable 地址
- 遇到跨域、鉴权、密码暴露、接口风格不一致等问题

根因：

- 没把业务系统当成统一接入层

正确做法：

- 前端只调业务系统接口
- 业务系统通过 go-common 统一代理工作流能力

### 5. 把“业务保存”和“流程启动”硬写成一个黑盒接口

典型表现：

- 一个接口里既落业务表，又起流程
- 一旦中间失败，不知道该回滚业务还是补流程

根因：

- 职责边界没有拆开

正确做法：

1. 先调业务保存接口
2. 拿到 `bizId`
3. 再调 `POST /api/v1/workflow/process/start`

这样失败定位和补偿都会简单很多。

### 6. BPMN 节点里直接依赖业务私有变量

典型表现：

- 流程图里大量出现 `${bizSpecificApproverId}`、`${bizSpecificOwnerUserId}`、`${bizSpecificDispatchUserId}` 这类写法
- 流程只能在某一个业务系统里勉强复用

根因：

- 把业务字段直接当成平台级流程契约

正确做法：

- 优先使用标准 Flowable 人员配置能力
- 需要变量驱动时，优先使用标准变量：
  - `nextAssignee`
  - `nextCandidateUsers`
  - `nextCandidateGroups`

### 7. 流程图发布了，但调用的不是已发布版本

典型表现：

- UI 里明明改了流程
- 但运行时还是走旧逻辑

根因：

- 流程图只是保存了，没有真正发布
- 调用时 `processDefinitionKey` 不是你以为的那个流程

正确做法：

- 确认流程已经 `Publish`
- 确认启动接口里传的是正确的 `processDefinitionKey`
- 必要时去 `flowable-rest` 查定义列表确认版本

### 8. 角色、组、用户编码没有统一

典型表现：

- 节点配置了候选组，但待办没人收到
- 待办里显示一堆看不懂的组编码

根因：

- LDAP 组编码、业务角色码、Flowable 候选组编码没有归一

正确做法：

- 明确谁是“用户 ID”
- 明确谁是“角色码”
- 通过 `workflow.identity.role_aliases` 和 `group_aliases` 做统一映射
- BPMN 中使用统一后的稳定编码

### 9. 回调地址能配，但业务系统没真正处理业务状态

典型表现：

- `callbackUrl` 配了
- `/api/v1/workflow/callback` 也收到了
- 但业务表状态完全没变

根因：

- 以为 callback 会自动修改你的业务表
- 但实际上 go-common 只负责接收和解析回调，不会凭空知道你的业务状态字段怎么更新

正确做法：

- 把 `/api/v1/workflow/callback` 当成“流程事件通知入口”
- 在业务系统里根据事件类型、节点 ID、流程状态去更新自己的业务表

### 10. 不区分待办、已办、办理记录、进度时间线

典型表现：

- 前端把所有接口混着用
- 页面上要么重复显示，要么信息断裂

正确理解如下：

- `todo`
  - 看“现在等谁处理”
- `done`
  - 看“我真正完成过哪些任务”
- `progress-timeline`
  - 看“流程主链路实际走到了哪”
- `task-records`
  - 看“某个节点发生过哪些办理动作，如认领、委派、转办、完成”
- `action-timeline`
  - 看“动作审计流”，不建议直接当主流程步骤页

如果前端只想做一个主进度页，优先组合：

- `progress-timeline`
- `task-records`

而不是直接拿 `action-timeline` 当主页面。

## 3. 总体架构与职责边界

推荐架构固定为四层：

1. `flowable-ui`
   - 负责流程图、表单模型、部署发布、身份源接入、节点人/组配置
2. `flowable-rest`
   - 负责流程运行态和历史态接口
3. `LDAP`
   - 负责用户、组、角色、岗位等身份数据
4. 业务系统 + `go-common/workflow`
   - 业务系统负责业务数据、业务接口、业务状态、LDAP 关系同步
   - `go-common/workflow` 负责标准工作流 API、callback、进度、时间线、记录聚合

### 3.1 Flowable 平台负责什么

- `flowable-ui`
  - 负责 BPMN 建模
  - 负责表单模型管理
  - 负责流程部署发布
  - 负责在 UI 中选择用户、候选用户、候选组、固定办理人
- `flowable-rest`
  - 负责流程运行时接口
  - 负责供业务系统通过 `go-common` 调用
- Flowable 平台数据库
  - 负责流程、历史、表单、部署、身份元数据存储
- Flowable 平台 LDAP
  - 负责用户、组、角色来源
  - 负责支撑 Flowable UI 中的身份选择和运行时 candidate 解析

这意味着：

- Flowable 平台自己的数据库、LDAP，本来就属于平台侧配置
- 业务系统默认不需要再承担 Flowable 平台 identity 的职责

### 3.2 `go-common/workflow` 负责什么

- 当前用户工作流上下文解析
- 启动流程
- 我的待办
- 我的已办
- 任务上下文
- 任务动作
- 流程进度视图
- 流程进度时间线
- 流程动作时间线
- 流程办理记录
- 我的办理记录
- 流程图视图
- Flowable REST 适配
- 表单引用元数据输出
- 标准 callback 路由与读模型刷新

注意：

- 目录查询、自动分配、身份归一化这类能力在代码中仍然存在
- 其中：
  - `workflow.directory.*`
    - 属于业务系统侧目录查询增强能力
    - 不是“为了跑流程必须启用”的主路径前置项
  - `workflow.assignment.*`
    - 属于历史兼容或特殊动态分配能力
  - `workflow.identity.*`
    - 属于历史兼容身份归一能力

### 3.3 `go-common/workflow` 不负责什么

- 业务主表设计
- 业务详情组装
- 业务表单渲染
- 业务状态机
- 业务权限模型
- 行业专属字段语义
- 替代 Flowable 平台 LDAP identity
- 替代业务系统自己的业务状态回写逻辑
- 自动完成所有业务字段语义校验

### 3.4 业务系统必须自己负责什么

- 业务保存接口
- 业务详情接口
- 业务列表接口
- 业务字段校验
- 附件管理
- 业务状态流转
- 流程变量与业务字段映射
- callback 后业务主表状态更新
- 业务角色关系、组织关系同步到 LDAP

### 3.5 标准主路线与历史兼容路线

当前文档默认只推荐下面这条标准主路线：

- Flowable 平台自己连接 LDAP
- BPMN 节点优先用 `candidateGroups / candidateUsers / assignee`
- 业务系统通过 `go-common` 调用 Flowable REST
- 业务系统收到 callback 后更新自己的业务状态

当前代码里仍然保留下面这条历史兼容路线：

- 业务系统运行时自己查 LDAP
- 通过 `workflow.assignment.*`
- 再借助 `nextAssignee / nextCandidateUsers / nextCandidateGroups` 临时算审批人

这条兼容路线不会在本标准文档中作为新项目主路径推荐。

另外单独说明：

- `workflow.directory.*`
  - 不等于这条历史兼容路线本身
  - 它也可以作为业务系统侧目录查询增强能力单独启用
  - 例如为 `/api/v1/workflow/me`、`/api/v1/workflow/org/**` 这类接口提供目录数据

## 4. 标准接入顺序

标准调用链路如下：

1. 用户登录，业务系统在请求上下文里放入：
   - `userId`
   - `userName`
   - `tenantId`
   - `systemCode`
   - `groups`
   - `roles`
2. 前端点击“提交申请”。
3. 前端先调用业务保存接口。
4. 业务后端写自己的业务表，生成 `bizId`。
5. 前端或业务后端调用 `POST /api/v1/workflow/process/start`。
6. 工作流返回 `processInstanceId`。
7. 业务后端把 `bizId` 与 `processInstanceId` 绑定。
8. 后续：
   - 我的待办、我的已办走工作流标准接口
   - 业务详情走业务系统自己的详情接口
   - 处理页同时加载业务详情 + 工作流上下文 + 进度 + 动作时间线

## 5. 推荐配置

下面只保留工作流接入真正需要关心的配置。

### 5.0 先记住标准主路径

标准主路径只有这一条：

- 业务系统保存业务数据
- 业务系统调用 go-common 标准工作流接口
- go-common 调 Flowable REST
- Flowable 按 BPMN 中的 `assignee / candidateUsers / candidateGroups` 流转
- Flowable 自己通过 LDAP 识别用户、组、候选组
- Flowable 回调业务系统标准 callback 接口
- 业务系统更新业务状态、展示待办、已办、进度、记录

按这条主路径接入时，业务系统默认只需要关心：

- `workflow.api.*`
- `workflow.flowable.*`
- `workflow.context.*`

其余配置全部属于：

- 可选增强能力
- 历史兼容能力
- 特殊动态场景能力

不要把下面这些能力误解为新项目默认必配：

- `workflow.identity.*`
- `workflow.directory.*`
- `workflow.assignment.*`
- `workflow.formref.*`
- `workflow.records.*`

### 5.0.1 审批人到底怎么配置

开发接入时，先不要急着问“接口里该传哪个字段”，而是先判断这个节点属于哪一类：

1. 固定职责节点
   - 例如“市级审核组”“省级审核组”“财务复核组”
   - 节点归属长期稳定
   - 推荐直接在 BPMN 里配置：
     - `candidateGroups`
     - `candidateUsers`
     - `assignee`
2. 动态计算节点
   - 例如“根据业务表中的当前责任人决定下一办理人”
   - 例如“根据地区、类型、金额实时算下一审批组”
   - 这类节点才使用：
     - `nextAssignee`
     - `nextCandidateUsers`
     - `nextCandidateGroups`

最简单的判断口诀：

- 长期稳定职责，用固定配置
- 运行时每单都可能不同，用动态变量

### 5.0.2 单个节点多个组到底是什么意思

如果一个节点配置：

```xml
flowable:candidateGroups="role_city_reviewer,role_province_reviewer"
```

它的真实含义是：

1. 这是一个共享候选池
2. 市级审核组的人可以处理
3. 省级审核组的人也可以处理
4. 任意一个组里的任意一个人处理一次，这个节点就结束

也就是：

- OR
- 任一组可处理

不是：

- 先市级后省级
- 两个组都必须处理
- 自动串成两级审批

正确建模方式要分清：

1. 任意一组处理即可
   - 一个节点，多个 `candidateGroups`
2. 组 A 之后必须组 B
   - 两个串行节点
3. 组 A 和组 B 都要各处理一次
   - 并行网关拆两个节点

### 5.0.3 为什么正式流程里不能写死测试账号

下面这种写法不是正式流程标准：

```xml
flowable:assignee="qxtest"
```

同类错误还包括：

- `flowable:assignee="test"`
- `flowable:assignee="admin"`

原因不是“Flowable 不能跑”，而是：

1. 它把职责节点错误地绑定成了某个测试账号
2. 流程设计人员、开发人员、实施人员会被误导
3. 上正式环境后容易直接把任务派给错误的人
4. 后续即使要切到动态变量，也容易留下理解冲突

正式项目只推荐两种路线：

1. 节点就是固定职责
   - 用 `candidateGroups / candidateUsers / assignee`
2. 节点必须动态计算
   - 用 `${nextAssignee}` / `${nextCandidateUsers}` / `${nextCandidateGroups}`

### 5.0.4 为什么不要固定配置和动态变量混用

一个节点只选一种模式：

1. 固定模式
2. 动态模式

不要混用。

反例 1：

- BPMN 写死：
  - `flowable:candidateGroups="role_city_reviewer"`
- 业务系统又传：
  - `nextCandidateGroups=["role_province_reviewer"]`

反例 2：

- BPMN 写死：
  - `flowable:assignee="qxtest"`
- 业务系统又传：
  - `nextAssignee="lisi"`

反例 3：

- 同一个 `userTask` 里同时存在：
  - `flowable:candidateGroups="role_city_reviewer"`
  - `flowable:assignee="${nextAssignee}"`

这些写法的共同问题是：

1. BPMN 看起来是一套规则
2. 业务代码又像是另一套规则
3. 线上排障时很难判断到底谁应该生效

所以平台规范要收敛成一句话：

- 固定节点就让 BPMN 自己表达清楚
- 动态节点就让 BPMN 明确读取标准变量
- 同一个节点不要两套都上

### 5.1 最小配置示例

```yaml
workflow:
  api:
    enabled: true
    prefix: "/api/v1/workflow"
    sso_enabled: true
  callback:
    path: "/api/v1/workflow/callback"
    secret: ""
    public_base_url: "http://127.0.0.1:9080"
  flowable:
    base_url: "http://127.0.0.1:8087/flowable-rest/service"
    username: "rest-admin"
    password: "PLEASE_CHANGE"
    timeout_seconds: 15
  context:
    user_id_strategy: "username_suffix"
    user_id_delimiter: "#"
```

### 5.2 配置项含义

先记住一条总原则：

- Flowable 平台自己的数据库、LDAP 配在 Flowable 平台
- 业务系统自己的主路径接入只需要关心 `workflow.api.* + workflow.callback.* + workflow.flowable.* + workflow.context.*`
- 其余配置分为“可选增强能力”和“历史兼容路线”

#### `workflow.flowable.*`

- `base_url`
  - Flowable REST 根地址。
  - 示例：`http://127.0.0.1:8087/flowable-rest/service`
- `username`
  - Flowable REST 服务账号。
- `password`
  - Flowable REST 服务密码。
- `timeout_seconds`
  - 调用 Flowable REST 的超时时间。

这是业务系统访问 Flowable 运行时接口的配置，不是：

- Flowable 平台数据库配置
- Flowable 平台 LDAP 配置

#### `workflow.api.*`

- `enabled`
  - 是否注册标准工作流接口。
- `prefix`
  - 工作流接口前缀，正式环境推荐统一为 `/api/v1/workflow`。
- `sso_enabled`
  - 是否要求登录态。

#### `workflow.callback.*`

- `path`
  - Flowable 回调接收路径。
  - 推荐固定为 `/api/v1/workflow/callback`。
- `secret`
  - 回调签名密钥。
  - 只影响业务系统“收到 callback 后是否验签”。
- `public_base_url`
  - Flowable 回调业务系统时访问的外部基地址。
  - 启动流程时拼接 `variables.callbackUrl` 应优先使用这个值。
  - 如果 Flowable 不在同一台机器，这里绝不能写 `localhost`。

#### 标准推荐增强：`workflow.context.*`

- `user_name_header`
  - 读取当前用户显示名的 Header。
- `system_code_header`
  - 读取系统编码的 Header。
- `groups_header`
  - 读取用户组列表的 Header。
- `roles_header`
  - 读取角色列表的 Header。

这组配置主要用于把业务系统当前登录态映射为工作流上下文。
它属于标准主路径推荐增强，不属于历史兼容能力。

这里要明确一条边界：

- `workflow.context.*`
  - 负责“当前登录用户如何透传给工作流接口”
- `workflow.identity.*`
  - 负责“不同身份编码之间如何做兼容归一”

标准主路径只要求你把当前用户透传清楚，不要求你额外做角色别名映射。

#### 标准推荐增强：`workflow.formref.*`

- `db_instance`
  - 用于表单引用解析的数据库实例名。

当前标准策略是：

- 默认优先走 REST 解析表单引用
- 只有在纯 REST 不能稳定解析时，才考虑启用 DB fallback

因此：

- `workflow.formref.db_instance` 不是默认必配
- 它属于可选增强能力

如果启用 DB fallback，必须保证：

- `workflow.formref.db_instance` 指向的 Flowable 元数据库
- 与 `workflow.flowable.base_url` 对应的是同一套 Flowable 环境

这里要把最容易混淆的点说清楚：

1. `workflow.formref.db_instance`
   - 不是让业务系统去“接管 Flowable 平台数据库”
   - 只是 go-common 在“表单引用解析”这个小能力上，必要时额外查一次 Flowable 元数据
2. 它查询的目标库，通常就是：
   - Flowable UI / Flowable REST 正在使用的那套 Flowable 平台数据库
3. 它不负责：
   - 替代 `workflow.flowable.base_url`
   - 替代 Flowable REST
   - 替代业务系统自己的业务库

可以直接把它理解成：

- `workflow.flowable.*`
  - 主通道
  - 用来调用 Flowable REST
- `workflow.formref.db_instance`
  - 备用增强通道
  - 只在表单引用解析不稳定时，补一条数据库读取能力

如果你的项目压根不需要 `form-ref`，或者 REST 已经能稳定解析表单引用：

- 那就不要配 `workflow.formref.db_instance`
- 保持最小接入即可

##### `workflow.formref.db_instance` 什么时候建议配置

建议配置的典型场景：

1. 你的前端页面会调用：
   - `GET /api/v1/workflow/tasks/{id}/form-ref`
2. 你的流程节点挂了 `formKey`，并且前端需要根据 `form-ref` 结果决定展示哪个页面或哪个表单组件
3. 你已经验证过：
   - 纯 REST 路径下，某些流程定义、表单引用、版本切换场景解析不稳定
4. 你明确知道业务系统连接的是哪一套 Flowable 环境，并且能拿到同环境的 Flowable 元数据库连接信息

不建议配置的场景：

1. 前端根本不用 `form-ref`
2. 你只做流程发起、待办、已办、处理，不需要表单引用解析
3. 纯 REST 已经足够稳定
4. 你无法保证数据库和 `workflow.flowable.base_url` 是同一套 Flowable 环境

##### `workflow.formref.db_instance` 怎么配置

标准写法分两段：

第 1 段，在 `workflow` 下声明要使用哪个数据库实例名：

```yaml
workflow:
  api:
    enabled: true
    prefix: "/api/v1/workflow"
  callback:
    path: "/api/v1/workflow/callback"
  flowable:
    base_url: "http://127.0.0.1:8087/flowable-rest/service"
    username: "rest-admin"
    password: "test"
  formref:
    db_instance: "flowable_meta"
```

第 2 段，在 `databases.mysql` 下真正定义这个实例：

```yaml
databases:
  mysql:
    default:
      db_name: default_mysql
      mode: single
      host: 127.0.0.1
      port: 3306
      user: root
      password: "123456"
      database: biz_app
      charset: utf8mb4
      parse_time: true
      loc: Local

    flowable_meta:
      db_name: flowable_meta
      mode: single
      host: 127.0.0.1
      port: 3307
      user: flowable_app
      password: "flowable"
      database: flowable_681_app
      charset: utf8mb4
      parse_time: true
      loc: Local
```

这里要逐个理解：

- `workflow.formref.db_instance: "flowable_meta"`
  - 表示 go-common 在做表单引用 DB fallback 时，去找名为 `flowable_meta` 的数据库实例
- `databases.mysql.flowable_meta`
  - 才是这个实例真正的连接参数定义
- `database: flowable_681_app`
  - 才是实际连接到的 Flowable 平台数据库名

也就是说：

- `db_instance`
  - 是实例名引用
- `database`
  - 是真实数据库名

这两个概念不要混掉。

##### `workflow.formref.db_instance` 配置后的真实效果

配了以后，不代表所有工作流能力都改走数据库。

真实效果只有一个：

- 当 go-common 需要做表单引用解析时，可以在 REST 不够稳定的情况下，多一条数据库读取元数据的兜底路径

它不会导致下面这些变化：

- 不会替代流程启动接口
- 不会替代待办查询接口
- 不会替代任务处理接口
- 不会让业务系统绕过 Flowable REST 直接跑流程

##### `workflow.formref.db_instance` 配错后最常见的表现

1. `db_instance` 名称写了，但 `databases.mysql` 下面根本没定义这个实例
   - 结果：启动时报数据库实例找不到，或者运行时解析失败
2. 实例定义了，但连到的是另一套 Flowable 环境
   - 结果：表单引用、流程定义、节点信息错位
3. `workflow.flowable.base_url` 指向测试环境，`flowable_meta` 却指向本地
   - 结果：REST 和 DB 查询结果互相打架
4. 明明前端不使用 `form-ref`，却额外配置了一套 `flowable_meta`
   - 结果：增加配置复杂度，但没有实际收益

开发时可以直接用这条判断规则：

- 没有 `form-ref` 页面需求，先不配
- 有 `form-ref` 页面需求，先只走 REST
- 确认 REST 不稳定，再补 `workflow.formref.db_instance`

这里要特别注意一条和旧版本不同的行为：

- 当前版本中，如果不配置 `workflow.formref.db_instance`
  - 就是 `REST-only`
  - 不会再隐式回退到业务默认库 `orm.DB`

#### 标准推荐增强：`workflow.records.*`

- `db_instance`
  - 用于读写 `workflow_task_records` 的数据库实例名。
  - 不配置时当前默认走业务默认库 `orm.DB`。
  - 如果希望流程办理记录与业务库分离，可以单独指定一个数据库实例。

`workflow.records.*` 属于工作流记录增强能力，不是：

- Flowable 平台运行库配置
- 新项目最小接入必配项

如果你的前端只需要：

- 启动流程
- 查询待办
- 查询已办
- 办理任务
- 查询进度

而不依赖自定义动作审计、任务办理轨迹增强能力：

- 那就可以先不配 `workflow.records.db_instance`
- 保持默认库或暂不启用增强模式即可

这里也要区分两件事：

1. Flowable 平台数据库
   - 是 Flowable 引擎自己的运行库、历史库、部署库、表单元数据存储
2. `workflow_task_records`
   - 是 go-common 自己的工作流办理记录表
   - 只服务于 go-common 的步骤明细、办理记录、动作补充展示

所以：

- `workflow.records.db_instance`
  - 指向的是“这张 go-common 记录表要落在哪个数据库实例”
- 它不是在配置 Flowable 平台库地址
- 它也不会替代 `workflow.flowable.base_url`

推荐理解方式：

- 小项目
  - 直接不配
  - 如果业务默认库 `orm.DB` 已初始化，记录就默认落业务库
  - 如果业务默认库没初始化，这块记录能力不会报错强制中断，但不会有持久化记录表可用
- 需要隔离工作流记录数据的项目
  - 再单独指定一个数据库实例

##### `workflow.records.db_instance` 怎么配置

如果你希望 `workflow_task_records` 不落默认业务库，也可以按和 `formref` 类似的方式单独指定：

```yaml
workflow:
  records:
    db_instance: "workflow_records"

databases:
  mysql:
    workflow_records:
      db_name: workflow_records
      mode: single
      host: 127.0.0.1
      port: 3306
      user: root
      password: "123456"
      database: biz_app
      charset: utf8mb4
      parse_time: true
      loc: Local
```

含义是：

- `workflow.records.db_instance`
  - 指定 go-common 的 `workflow_task_records` 这张表落到哪个数据库实例
  - 这张表属于 go-common 自己的业务侧记录表，不是 Flowable 引擎表

推荐理解方式：

- `workflow.formref.db_instance`
  - 通常指向 Flowable 元数据库
  - 只服务于表单引用解析 fallback
- `workflow.records.db_instance`
  - 通常指向业务系统默认库，或业务系统自己单独划出的记录库
  - 不建议默认写成 `flowable_meta`
  - 因为 `workflow_task_records` 不是 Flowable 平台表

如果你不关心记录表隔离：

- 就不要配
- 默认走业务系统当前主库即可

#### 5.2.1 到底什么时候业务系统需要感知 Flowable 平台数据库

当前标准结论如下：

1. 新项目最小接入
   - 不需要关心 Flowable 平台数据库连接信息
   - 只需要：
     - `workflow.api.*`
     - `workflow.flowable.*`
2. 只有在启用下面能力时，业务系统才需要额外感知某个数据库实例：
   - `workflow.formref.db_instance`
   - `workflow.records.db_instance`
3. 这两种“感知数据库”都属于增强能力，不是主线路径

换句话说：

- 业务系统接入工作流，不等于业务系统必须默认配置一套 `flowable_meta` 数据源
- 如果你只是：
  - 发起流程
  - 查待办
  - 查已办
  - 处理任务
  - 查步骤
  - 接 callback
- 那完全可以先不配 Flowable 元数据库

这里再强调一次：

- `workflow.formref.db_instance`
  - 让业务系统额外感知的是 Flowable 元数据库
- `workflow.records.db_instance`
  - 让业务系统额外感知的是 `workflow_task_records` 的落库实例
  - 它不等于 Flowable 元数据库

#### 5.2.2 `workflow.flowable.*` 和 `flowable_meta` 指向不同环境会怎样

这是配置里最危险的一类错误。

如果出现下面这种情况：

- `workflow.flowable.base_url`
  - 指向测试环境 A 的 Flowable REST
- `workflow.formref.db_instance`
  - 却连到了本地或环境 B 的 Flowable 元数据库

那就会出现典型错乱：

1. 通过 REST 启动的是环境 A 的流程
2. 通过 DB 解析出来的表单、定义、元数据却来自环境 B
3. 最终表现为：
   - 表单引用不匹配
   - 任务节点信息看起来错位
   - 明明流程已经发布，但解析出来还是旧模型

所以只要启用了 DB fallback，就必须遵守一条硬规则：

- `workflow.flowable.base_url` 与 `workflow.formref.db_instance` 必须指向同一套 Flowable 环境

如果你不能保证这点：

- 宁可先不要配 `workflow.formref.db_instance`
- 先只走 REST 主路线

#### 5.2.3 Flowable 配置避坑清单

这部分建议开发和运维一起核对，很多“看起来接口通了、实际数据是错的”都出在这里。

1. `workflow.flowable.base_url` 必须指向 REST，不是 UI
   - 正确示例：`http://host:9090/flowable-rest/service`
   - 错误示例：`http://host:9091/flowable-ui/`
   - 如果配成 UI 地址，最直接的表现通常是启动、待办、完成任务等接口全部报 REST 调用错误
2. `workflow.formref.db_instance` 只有在确实需要 `form-ref` DB fallback 时再配置
   - 没有 `form-ref` 页面需求，就不要为了“看起来完整”多配一套 `flowable_meta`
   - 否则只会增加连接、密码、环境一致性这几类额外维护成本
3. `workflow.formref.db_instance` 一旦配置，就必须和 `workflow.flowable.base_url` 指向同一套 Flowable 环境
   - REST 指测试，DB 连本地，是最危险也最隐蔽的一类错误
   - 典型表现是：流程能启动，但表单引用、节点信息、流程定义版本看起来对不上
4. `workflow.records.db_instance` 不建议默认写成 `flowable_meta`
   - 因为 `workflow_task_records` 是 go-common 业务侧记录表，不是 Flowable 引擎表
   - 默认更合理的选择是：
     - 不配置，走业务默认库
     - 或显式指定独立的业务记录库
5. 新项目首次接入，不要先开 `workflow.directory.* / workflow.assignment.* / workflow.identity.*`
   - 先把“业务保存 -> 流程启动 -> 待办处理 -> callback 回写”主路线跑通
   - 再决定是否需要目录增强、审批人动态计算、身份归一
6. 看到文档里的 `PLEASE_CHANGE`、`test`、`flowable` 这类值，要先判断它是“示例占位”还是“你当前环境真实值”
   - 不要把示例值原样复制到测试或正式环境
   - 也不要因为示例值能本地跑通，就误以为其他环境也能直接照抄

#### 历史兼容：`workflow.identity.*`

- `role_aliases`
  - 用于把不同来源的角色编码归一为 Flowable 使用的角色码。
- `group_aliases`
  - 用于统一非角色型组编码。

这组配置当前代码能力仍然存在，但不再是新项目最小接入前置条件。

##### `workflow.identity.*` 什么时候才建议配置

建议配置的场景：

1. 你的系统里同时存在多套角色编码来源
   - 例如 LDAP 角色码、JWT 角色码、历史业务角色码
2. 你希望 BPMN 里只保留一套稳定候选组编码
3. 你不想因为登录来源切换或历史角色改名，导致 BPMN 一起改

不建议优先配置的场景：

1. 新项目首次接入
2. 你的 Flowable UI、LDAP、业务系统角色编码本来就已经统一
3. 你只是为了“看起来配置全一点”而先把这组能力打开

一句话理解：

- `workflow.identity.*` 是编码归一桥接层
- 不是新项目标准主路线的核心前置条件

##### `workflow.identity.*` 怎么配置

示例：

```yaml
workflow:
  identity:
    role_aliases:
      LDAP_ROLE_CITY_REVIEWER: CITY_REVIEWER
      LEGACY_ROLE_17: CITY_REVIEWER
      JWT_ROLE_CITY_REVIEW: CITY_REVIEWER
    group_aliases:
      CITY_REVIEW_USERS: city_review_users
      CITY_REVIEW_GROUP: city_review_users
```

这里的含义是：

- 左边
  - 各种历史来源、不同系统、不同协议里的原始编码
- 右边
  - 你最终想在 Flowable / BPMN / 前端展示里统一使用的稳定编码

例如：

- BPMN 最终统一写：
  - `role_CITY_REVIEWER`
- 不管登录上下文里拿到的是：
  - `LDAP_ROLE_CITY_REVIEWER`
  - `LEGACY_ROLE_17`
  - `JWT_ROLE_CITY_REVIEW`
- 最终都可以归一到：
  - `CITY_REVIEWER`

##### `workflow.identity.*` 配错后会怎样

最常见的表现：

1. 同一个角色在不同接口里显示成不同编码
2. 候选组明明配对了，但前端展示或权限判断对不上
3. 待办能查到，但页面解释不清楚“这个组到底是谁”

所以这组配置的价值是：

- 提升编码统一性
- 降低历史系统迁移成本

而不是：

- 替代 Flowable 平台 LDAP
- 替代 BPMN 里的候选组建模
- 替代业务系统的人岗关系维护

#### 按需增强：`workflow.directory.*`

- `provider`
  - 目录服务来源。
  - 常见值：`none`、`ldap`

当前公司标准主路线默认不要求业务系统为了“跑流程”单独启用目录 provider。

但只要业务系统还要通过 go-common 对外提供目录查询接口，例如：

- `GET /api/v1/workflow/me`
- `GET /api/v1/workflow/me/manager`
- `GET /api/v1/workflow/me/department`
- `GET /api/v1/workflow/org/**`

那就应按需启用：

- `workflow.directory.provider=ldap`

##### `workflow.directory.*` 什么时候才建议配置

建议配置的场景：

1. 你的某些接口需要在业务系统内直接查：
   - 用户信息
   - 上级信息
   - 部门信息
2. 你需要启用 `/api/v1/workflow/me`、`/api/v1/workflow/org/**` 这类目录接口
3. 你是老项目迁移
4. 你当前仍然依赖“业务系统运行时自己查 LDAP”

不建议优先配置的场景：

1. 新项目首次接入
2. 你只是为了流程发起、待办、已办、处理、回调这些标准能力
3. 你并不需要业务系统额外提供目录查询接口

一句话理解：

- `workflow.directory.*` 是业务系统侧目录读取能力
- 不是 Flowable 平台 LDAP 的替代品
- 也不等于“只能给历史项目用”

##### `workflow.directory.*` 怎么配置

示例：

```yaml
workflow:
  directory:
    provider: ldap
    ldap:
      addr: "ldap://127.0.0.1:8389"
      bind_dn: "cn=admin,dc=example,dc=com"
      bind_password: "password"
      base_dn: "dc=example,dc=com"
      people_ou: "ou=people"
      department_ou: "ou=departments"
      position_ou: "ou=positions"
      use_tls: false
```

字段含义：

- `provider`
  - 目录服务来源
  - `none` 表示不启用业务系统侧目录服务
  - `ldap` 表示业务系统自己也去连 LDAP
- `addr`
  - LDAP 地址
- `bind_dn / bind_password`
  - LDAP 绑定账号和密码
- `base_dn`
  - 根 DN
- `people_ou`
  - 人员 OU
- `department_ou`
  - 部门 OU
- `position_ou`
  - 岗位 OU
- `use_tls`
  - 是否启用 TLS

##### `workflow.directory.*` 配置后的真实效果

配了以后，表示：

- go-common 可以在业务系统侧直接查目录信息

典型用途包括：

- `GET /api/v1/workflow/me/manager`
- `GET /api/v1/workflow/me/department`
- 某些历史兼容分配逻辑里，需要先查目录再算审批人

它不会自动带来下面这些效果：

- 不会自动让 Flowable UI 看到 LDAP 用户
- 不会自动让 Flowable REST 改成 LDAP 登录
- 不会自动把 BPMN 节点办理人改成标准主路线

##### `workflow.directory.*` 配错后会怎样

最常见的表现：

1. 业务系统内查用户、部门、上级接口失败
2. 兼容分配逻辑算不出人
3. 业务系统和 Flowable 平台看到的组织结构不一致

所以如果你不是明确要走历史兼容路线：

- 先保持 `provider: none`
- 不要默认启用它

#### 历史兼容：`workflow.assignment.*`

- `provider`
  - 自动分配来源。
  - 常见值：`none`、`directory`、`ldap`
- `variable_keys.assignee`
  - 下一办理人变量名，默认推荐 `nextAssignee`
- `variable_keys.candidate_users`
  - 下一候选用户变量名，默认推荐 `nextCandidateUsers`
- `variable_keys.candidate_groups`
  - 下一候选组变量名，默认推荐 `nextCandidateGroups`

这组配置对应的是：

- 业务系统运行时自己算审批人的历史兼容路线

它不是当前公司标准主路线。

##### `workflow.assignment.*` 什么时候才建议配置

建议配置的场景：

1. 老流程 BPMN 已经大量使用：
   - `${nextAssignee}`
   - `${nextCandidateUsers}`
   - `${nextCandidateGroups}`
2. 业务系统必须在运行时动态决定下一步给谁
3. 你暂时还不能把人岗角色关系完全沉淀到 LDAP + Flowable UI 配置里

不建议优先配置的场景：

1. 新项目首次接入
2. 节点职责本来就稳定，完全可以直接在 BPMN 中配候选组
3. 只是为了“保留灵活性”而预先开启运行时分配

一句话理解：

- `workflow.assignment.*` 是“业务系统运行时自己算审批人”的兼容能力
- 不是新项目标准主路线

##### `workflow.assignment.*` 怎么配置

示例 1：保持关闭

```yaml
workflow:
  assignment:
    provider: none
```

示例 2：按目录服务输出 `next*` 变量

```yaml
workflow:
  directory:
    provider: ldap
    ldap:
      addr: "ldap://127.0.0.1:8389"
      bind_dn: "cn=admin,dc=example,dc=com"
      bind_password: "password"
      base_dn: "dc=example,dc=com"
      people_ou: "ou=people"
      department_ou: "ou=departments"
      position_ou: "ou=positions"
      use_tls: false

  assignment:
    provider: directory
    variable_keys:
      assignee: "nextAssignee"
      candidate_users: "nextCandidateUsers"
      candidate_groups: "nextCandidateGroups"
```

字段含义：

- `provider`
  - `none`
    - 不启用运行时自动分配
  - `directory`
    - 基于已配置的目录服务计算分配结果
  - `ldap`
    - 直接基于 LDAP 计算分配结果
- `variable_keys.assignee`
  - 输出到哪个流程变量名，默认推荐 `nextAssignee`
- `variable_keys.candidate_users`
  - 输出到哪个流程变量名，默认推荐 `nextCandidateUsers`
- `variable_keys.candidate_groups`
  - 输出到哪个流程变量名，默认推荐 `nextCandidateGroups`

##### `workflow.assignment.*` 配置后的真实效果

配了以后，表示：

- go-common 可以在业务系统运行时，按兼容规则算出下一办理人或候选池
- 再把结果写进 `next*` 变量，供 BPMN 的 `${nextAssignee}` 等表达式消费

它不会自动带来下面这些效果：

- 不会替代 Flowable UI 中直接可见的节点人/组配置
- 不会让 BPMN 自动变成标准主路线
- 不会减少流程设计人员和开发之间的理解成本

##### `workflow.assignment.*` 配错后会怎样

最常见的表现：

1. 流程能启动，但下一节点没人收到待办
2. 变量名和 BPMN 里写的不一致
3. 同一流程在不同系统里行为不一致
4. 流程设计人员在 UI 里看不出节点到底怎么分配

开发时可以直接用这条判断规则：

- 能用候选组解决，就不要开 assignment
- 非开不可，再明确写清楚：
  - 来源是什么
  - 变量名是什么
  - BPMN 消费的是什么

### 5.3 业务程序代码如何接入

只配 `config.yaml` 还不够，业务后端还必须在代码里把工作流标准路由注册进自己的 HTTP 服务。

最常见的接入方式就是：

1. 初始化你自己的业务系统配置
2. 初始化登录、RBAC、数据库、Redis 等基础能力
3. 创建业务系统自己的 `HTTPServer`
4. 先注册你自己的业务接口
5. 再调用 `workflowapi.MustRegisterFromConfig(server)` 注册工作流标准接口
6. 最后执行 `server.Prepare()` 和 `server.Run(...)`

#### 最小后端接入示例

```go
package main

import (
    commonhttp "github.com/goodbye-jack/go-common/http"
    rbacbase "github.com/goodbye-jack/go-common/rbac"
    workflowapi "github.com/goodbye-jack/go-common/workflow/api"
)

func main() {
    rbacbase.InitRoleMapping([]string{
        "ADMIN_ROLE",
        "DEFAULT_ROLE",
    })

    server := commonhttp.NewHTTPServer("demo-service")

    // 这里注册你自己的业务接口
    registerBizRoutes(server)

    // 这里注册 go-common 提供的标准工作流接口
    workflowapi.MustRegisterFromConfig(server)

    server.Prepare()
    server.Run(":9080")
}
```

#### 这段代码实际做了什么

- `workflowapi.MustRegisterFromConfig(server)`
  - 按 `config.yaml` 里的 `workflow.*` 配置，自动创建 Flowable REST 客户端、标准工作流路由、callback 路由，以及按需启用目录服务、分配服务、表单引用服务
  - 自动把标准工作流接口挂到业务系统自己的服务里
  - 配置有问题时直接启动失败，避免系统“带病启动”
- `server.Prepare()`
  - 让 go-common 完成路由整理、鉴权元数据准备、权限策略落库等准备动作
- `server.Run(...)`
  - 正式对外提供业务接口和工作流接口

这里再展开成开发最关心的版本：

最小接入时，`workflowapi.MustRegisterFromConfig(server)` 至少会帮你接好：

1. 标准工作流 API
   - 如流程启动、待办、已办、步骤、办理记录、图形、callback
2. Flowable REST 调用客户端
   - 让这些 API 能正常访问 `workflow.flowable.base_url`
3. callback 接收路由
   - 路径来自 `workflow.callback.path`

只有在你额外配置或启用了增强能力时，它才会继续按需接入：

4. `formref` DB fallback
5. 目录服务
6. 分配服务
7. 身份归一能力

所以请不要误解成：

- 只要用了 `MustRegisterFromConfig`，业务系统就必须把所有 LDAP、directory、assignment、flowable_meta 全配齐

不是。

标准主路线下，最小代码接入和最小配置接入都应该尽量简单。

#### 什么时候调用最合适

推荐放在“业务路由注册完成之后、`server.Prepare()` 之前”。

推荐顺序如下：

```go
server := commonhttp.NewHTTPServer(serviceName)

// 1. 注册业务接口
biz.RouteAPI(server)

// 2. 注册工作流标准接口
workflowapi.MustRegisterFromConfig(server)

// 3. 准备并启动
server.Prepare()
server.Run(addr)
```

不推荐下面这种顺序：

- `server.Run()` 之后再注册
- 没有调用 `server.Prepare()`
- 业务接口还没注册完就中途启动

#### 如果要自定义目录服务或分配服务怎么办

默认推荐直接用：

```go
workflowapi.MustRegisterFromConfig(server)
```

只有在下面这些场景，才需要改用带 `options` 的注册方式：

- 你不想使用配置文件里的默认 LDAP 目录服务
- 你要注入自定义 `AssignmentService`
- 你要接入自定义表单引用解析服务
- 你要覆盖默认契约校验策略

示例：

```go
workflowapi.MustRegisterFromConfigWithOptions(server, workflowapi.RegisterOptions{
    DirectoryService:  myDirectoryService,
    AssignmentService: myAssignmentService,
    FormRefService:    myFormRefService,
    ContractPolicy:    myContractPolicy,
})
```

#### 业务后端除了注册工作流接口，还必须自己实现什么

工作流标准接口不替代你的业务接口。业务系统至少还要自己提供下面几类接口：

- 业务保存接口
  - 例如：`POST /api/v1/relic-preservation-alarms`
  - 负责写业务表、生成 `bizId`
- 业务详情接口
  - 例如：`GET /api/v1/relic-preservation-alarms/{bizId}`
  - 负责返回表单详情、附件、状态等业务数据
- 业务列表接口
  - 例如：草稿列表、我的申请列表、业务查询列表
- 业务状态更新逻辑
  - 例如：流程启动成功后，把业务单状态更新为“审批中”
  - 例如：收到回调后，把业务单状态更新为“已完成”“已驳回”“待补正”

要点只有一句话：

- `go-common/workflow` 负责流程能力
- 业务系统自己负责业务数据

#### 5.3.1 开发者最容易照抄成功的最小闭环

如果你现在只想知道“业务代码到底最少要做到什么，整个流程才能跑起来”，那就记下面 5 件事：

1. `config.yaml` 配好：
   - `workflow.api.*`
   - `workflow.flowable.*`
2. 启动代码里注册：
   - `workflowapi.MustRegisterFromConfig(server)`
3. 自己实现一个业务保存接口：
   - 负责生成 `bizId`
   - 负责把业务表数据落库
4. 前端或业务后端按两步调用：
   - 先调业务保存接口
   - 再调 `POST /api/v1/workflow/process/start`
5. 启动流程时传入：
   - `processDefinitionKey`
   - `bizId`
   - `bizType`
   - `title`
   - `variables.callbackUrl`
   - `variables.callbackEvents`

只要这 5 件事做对了，哪怕你先不启用下面这些增强项：

- `workflow.formref.db_instance`
- `workflow.records.db_instance`
- `workflow.directory.*`
- `workflow.assignment.*`
- `workflow.identity.*`

也仍然可以先把标准主路线跑通。

### 5.4 前后端怎么配合使用

标准用法不是“前端只调一个万能业务接口”，而是“业务保存”和“流程启动”分开。

#### 标准发起顺序

1. 前端填写业务表单
2. 前端调用业务保存接口
3. 业务后端保存业务表，返回 `bizId`
4. 前端或业务后端调用 `POST /api/v1/workflow/process/start`
5. 启动成功后，业务系统记录 `bizId` 与 `processInstanceId` 的关系
6. 后续待办、已办、进度、办理动作都走标准工作流接口
7. 业务详情、附件、业务状态展示继续走业务系统自己的接口

#### 推荐的前端调用拆分

- 发起页
  - 先调业务保存接口
  - 再调工作流启动接口
- 我的待办页
  - 调 `GET /api/v1/workflow/me/tasks/todo`
- 我的已办页
  - 调 `GET /api/v1/workflow/me/tasks/done`
- 任务处理页
  - 调业务详情接口
  - 调 `GET /api/v1/workflow/tasks/{id}/context`
  - 调 `GET /api/v1/workflow/tasks/{id}/form-ref`
  - 调 `GET /api/v1/workflow/biz/{bizId}/progress-timeline`
  - 调 `GET /api/v1/workflow/biz/{bizId}/task-records`
- 提交处理
  - 根据动作调用 `claim / unclaim / delegate / resolve / transfer / complete`

#### 一个最小的发起流程示例

前端或网关层发起时，推荐拆成两次 HTTP 调用。

第一步，保存业务：

```http
POST /api/v1/business-records
Content-Type: application/json

{
  "title": "通用审批测试",
  "category": "GENERAL_APPROVAL",
  "priority": "NORMAL"
}
```

假设返回：

```json
{
  "data": {
    "bizId": "BIZ-20260611-0001"
  },
  "message": "success"
}
```

第二步，启动流程：

```http
POST /api/v1/workflow/process/start
Content-Type: application/json

{
  "processDefinitionKey": "generic_approval_demo",
  "bizId": "BIZ-20260611-0001",
  "bizType": "generic_approval",
  "title": "通用审批测试",
  "name": "通用审批测试",
  "variables": {
    "starterId": "test1",
    "starterName": "测试用户1",
    "callbackUrl": "http://127.0.0.1:9080/api/v1/workflow/callback",
    "callbackEvents": "PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED"
  }
}
```

这样做的好处是：

- 业务表和流程实例职责清晰
- 任何一个环节失败都更容易补偿
- 开发人员更容易理解问题出在业务接口还是流程接口
- 不会把“保存业务”和“启动流程”硬耦合成一个黑盒接口

### 5.5 `flowable-ui`、`flowable-rest`、业务程序分别负责什么

很多人接入时会把这三层混在一起。这里直接拆开说明。

#### `flowable-ui` 负责什么

- 画流程图
- 配节点属性
- 配用户任务、候选人、候选组
- 配表单模型
- 发布流程定义
- 查看流程模型和管理后台信息

一句话概括：

- `flowable-ui` 是“流程设计和发布平台”

#### `flowable-rest` 负责什么

- 接收 go-common 发起的 REST 调用
- 启动流程实例
- 查询运行中任务
- 查询历史任务和历史流程
- 执行认领、委派、转办、完成等运行态动作

一句话概括：

- `flowable-rest` 是“流程引擎运行时服务”

#### 业务程序负责什么

- 保存业务数据
- 返回业务详情
- 注册 `go-common/workflow` 标准接口
- 提供业务页面
- 处理业务状态同步
- 决定哪些业务字段映射为流程变量

一句话概括：

- 业务程序是“真正对外提供业务功能的系统”

#### 最容易搞错的一点

业务系统不是直接接 `flowable-ui`。

正确关系是：

1. 流程设计人员在 `flowable-ui` 里画图并发布
2. 业务系统通过 `go-common/workflow` 调用 `flowable-rest`
3. 前端页面调用的是“业务系统接口”和“业务系统里暴露出来的标准工作流接口”

也就是说：

- 前端不直接调 `flowable-ui`
- 前端通常也不直接调 `flowable-rest`
- 前端应该调业务系统暴露出来的统一接口

## 8. 流程启动接口

### 8.1 `POST /api/v1/workflow/process/start`

#### 先记住这 6 条

1. 标准发起顺序始终是：
   - 先保存业务表
   - 再调用 `POST /api/v1/workflow/process/start`
2. `processDefinitionId` 和 `processDefinitionKey`
   - 二选一即可
   - 新项目更推荐固定传 `processDefinitionKey`
3. `bizId`
   - 应该先由业务系统生成并落库
   - 不建议把“启动流程成功后再反推业务主键”当标准做法
4. `variables`
   - 不是随便传
   - 必须和 BPMN 里真正使用的变量契约保持一致
5. 如果你们项目要依赖 callback 同步待办、已办、业务状态：
   - 启动时就必须同时考虑 `callbackUrl` 和 `callbackEvents`
6. 如果你不确定下一步审批人是不是“动态指定”：
   - 就不要先盲传 `nextAssignee / nextCandidateUsers / nextCandidateGroups`
   - 先确认 BPMN 是否真的按这些标准变量建模

#### 作用

- 启动一个新的流程实例。

#### 使用场景

- 业务保存成功后启动流程
- 管理后台手工补发流程
- 联调 BPMN 时直接验证流程定义 key 是否可用

#### 路径参数

- 无

#### 请求体字段

- `processDefinitionId`
  - 流程定义 ID
  - 与 `processDefinitionKey` 二选一
- `processDefinitionKey`
  - 流程定义 Key
  - 正式接入时更推荐使用这个
- `businessKey`
  - Flowable 业务键
  - 本平台标准接入时，应承载业务系统的 `bizId` 值
- `bizId`
  - 业务主键
- `bizType`
  - 业务类型
- `title`
  - 业务标题
- `name`
  - Flowable 实例名称
- `variables`
  - 启动时写入流程实例的变量集合

#### 字段使用建议

- `processDefinitionKey`
  - 推荐作为主用字段
  - 好处是部署新版本后通常不需要业务系统改代码
- `processDefinitionId`
  - 更适合调试、灰度或强制指定某个部署版本
  - 不建议作为长期主路径入参
- `bizId`
  - 推荐和业务表主键或业务唯一号一一对应
  - 这样后续查进度、回写状态、排查 callback 都最直接
- `businessKey`
  - 这是 Flowable 标准字段名，不建议业务项目自行改名
  - 在本平台标准里，它的职责是“把业务实例唯一标识写进 Flowable”
  - 也就是：`businessKey` 的值应当与 `bizId` 相同
  - 注意这里是“值相同、职责不同”
  - `bizId` 是业务系统自己的标识
  - `businessKey` 是 Flowable 用来保存这个标识的标准字段位
- `title / name`
  - 建议显式传
  - 不要完全依赖流程定义默认名称，否则待办列表和已办列表会不够直观
- `variables`
  - 只放“BPMN 真正需要使用的变量”和“回调需要透传的变量”
  - 不要把整份业务大对象无脑塞进流程变量

#### 请求体示例

```json
{
  "processDefinitionKey": "asset_approval_process",
  "businessKey": "BIZ-20260610-0001",
  "bizId": "BIZ-20260610-0001",
  "bizType": "asset_approval",
  "title": "资产审批申请示例",
  "name": "资产审批申请示例",
  "variables": {
    "starterId": "test1",
    "starterName": "测试用户1",
    "tenantId": "test-demo",
    "systemCode": "sysA",
    "nextAssignee": "test2",
    "callbackUrl": "http://127.0.0.1:9080/api/v1/workflow/callback",
    "callbackEvents": "PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED"
  }
}
```

#### 什么时候不要这样发

1. 业务表还没保存，就直接先发起流程
   - 这样最容易出现流程已经起来了，但业务主表没有对应数据
2. 同时传 `processDefinitionId` 和 `processDefinitionKey`，但自己都不确定实际希望走哪个
   - 标准接入里应保持单一策略
3. BPMN 明明用的是固定候选组，你却在启动时硬传 `nextAssignee`
   - 这样只会让开发误以为“接口传了变量，流程就一定按这个人走”
4. 远端 Flowable 联调时，`callbackUrl` 仍然写 `127.0.0.1` 或 `localhost`
   - 这样 callback 基本一定收不到
5. 把整个业务对象、附件列表、超大 JSON 全塞到 `variables`
   - 这会显著增加变量维护和排错成本

#### 最常见的 5 个误区

1. 以为 `process/start` 会自动帮你保存业务表
   - 不会
   - 业务数据落库永远是业务系统自己的职责
2. 以为把 `nextAssignee` 传进去，流程一定就会分给这个人
   - 不一定
   - 只有 BPMN 明确按标准变量契约建模时，这个变量才会生效
3. 以为不传 `title / name` 也没关系
   - 技术上可能能启动
   - 但待办、已办、进度展示会变得不直观
4. 以为 callback 只要在 YAML 里配置了就一定会回调
   - 不对
   - 启动请求里还必须明确带 `callbackUrl / callbackEvents`
5. 以为 `processDefinitionId` 比 `processDefinitionKey` 更“正式”
   - 长期接入恰恰通常相反
   - `processDefinitionKey` 对流程版本升级更稳定

#### 返回字段

- `processInstanceId`
  - 流程实例 ID
- `processDefinitionId`
  - 实际启动的流程定义 ID
- `businessKey`
  - Flowable 业务键
- `tenantId`
  - 租户编码

#### 请求示例

```bash
curl -X POST http://127.0.0.1:9080/api/v1/workflow/process/start \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{
    "processDefinitionKey":"asset_approval_process",
    "businessKey":"BIZ-20260610-0001",
    "bizId":"BIZ-20260610-0001",
    "bizType":"asset_approval",
    "title":"资产审批申请示例",
    "variables":{
      "starterId":"test1",
      "callbackUrl":"http://127.0.0.1:9080/api/v1/workflow/callback",
      "callbackEvents":"PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED"
    }
  }'
```

## 9. 待办、已办与办理记录接口

### 9.1 公共查询参数

以下 3 个列表接口共用同一套基础查询参数：

- `start`
  - 分页起始下标
- `size`
  - 分页大小
- `includeProgress`
  - 是否附带轻量进度摘要
- `title`
  - 按标题模糊过滤
- `bizType`
  - 按业务类型过滤
- `processDefinitionKey`
  - 按流程定义 key 过滤
- `activityId`
  - 按当前或历史节点 ID 过滤
- `actionType`
  - 仅办理记录接口有意义
  - 可选值例如：`START_PROCESS`、`CLAIM`、`UNCLAIM`、`DELEGATE`、`RESOLVE`、`TRANSFER`、`COMPLETE`
- `status`
  - 状态过滤
- `createdAfter`
  - 创建时间起始
- `createdBefore`
  - 创建时间结束
- `completedAfter`
  - 完成时间起始，仅已办更有意义
- `completedBefore`
  - 完成时间结束，仅已办更有意义

### 9.2 `GET /api/v1/workflow/me/tasks/todo`

#### 先记住这 4 条

- `todo` 只回答一个问题：
  - “现在还有哪些任务在等我处理”
- 待办页、工作台待办卡片、首页待办数量，优先都应该基于这个接口。
- 不要指望它返回历史办理轨迹。
- 也不要拿它去做“我参与过哪些动作”的审计查询。

#### 作用

- 查询当前登录人的待办任务。

#### 使用场景

- 我的待办列表
- 工作台卡片
- 待办搜索页

#### 查询参数示例

```text
start=0&size=20&includeProgress=true&bizType=asset_approval
```

#### 返回字段重点

- `items[].taskId`
- `items[].taskName`

## 11. 任务动作接口

### 11.1 职责边界

这一节非常重要，开发、测试、流程设计人员必须统一理解。

`go-common/workflow` 当前把任务相关接口明确拆成两类职责：

第一类，任务办理权管理接口：

- `claim`
- `unclaim`
- `delegate`
- `resolve`
- `transfer`

这 5 个接口只负责处理“这件任务现在由谁来办”。

它们解决的是：

- 候选任务是否已经被认领
- 当前办理人是否要把任务放回候选池
- 当前办理人是否要临时委派给别人
- 受托人处理完成后是否归还给原办理人
- 当前任务是否要彻底转交给另一个办理人

它们不解决的是：

- 流程是否流转到下一节点
- BPMN 网关走哪条线
- 退回、驳回、重审、补正应该走哪个分支

第二类，流程推进接口：

- `complete`

`complete` 只负责处理“流程往哪走”。

它解决的是：

- 当前节点处理完成
- 本次处理结果写入流程变量
- Flowable 根据变量和 BPMN 条件表达式决定下一节点

它不负责的是：

- 抢占候选任务
- 释放任务
- 委派
- 转办

可以这样理解：

- `claim / unclaim / delegate / resolve / transfer`
  - 管的是“谁来办”
- `complete`
  - 管的是“办完以后流程往哪走”

如果只记一句话，请记住：

- 想改办理人，用任务动作接口。
- 想推进流程，用 `complete`。

#### 5 秒决策口诀

拿到一个任务后，先问自己“我现在到底想改什么”：

1. 想把候选任务先拿到自己名下
   - `claim`
2. 想把已认领任务放回候选池
   - `unclaim`
3. 想临时让别人代处理，处理完还回我
   - `delegate`
4. 我是受托人，代处理已经完成，要还回原办理人
   - `resolve`
5. 想彻底交给别人继续办，后续不再回我
   - `transfer`
6. 想让流程真正往下一步走
   - `complete`

如果你连“现在是改办理权，还是改流程走向”都还没分清，就不要先发请求。

#### 最常见的 4 条正确顺序

1. 候选任务认领后处理
   - `claim` -> `complete`
2. 认领错了，放回候选池
   - `unclaim`
3. 临时委派给别人处理，处理完还要回原办理人
   - `delegate` -> 受托人 `resolve` -> 原办理人 `complete`
4. 彻底改由别人继续处理
   - `transfer` -> 新办理人 `complete`

#### 最容易犯错的 4 个误区

1. 以为 `delegate` 后受托人可以直接 `complete`
   - 不对
   - 标准委派链路是先 `resolve`，再回原办理人 `complete`
2. 以为 `transfer` 后任务还会回原办理人
   - 不对
   - `transfer` 是彻底转办，后续由新办理人直接继续
3. 以为 `claim / unclaim / delegate / resolve / transfer` 会推动 BPMN 往下走
   - 不对
   - 真正推动流程的是 `complete`
4. 以为退回、驳回、补正要靠“转办接口”实现
   - 不对
   - 这些都应通过 `complete + 变量 + BPMN 条件表达式` 实现

#### 最常见的无效组合

1. `delegate` 后，受托人直接 `complete`
   - 无效理解
   - 标准链路应先 `resolve`
2. `transfer` 后，原办理人还继续 `complete`
   - 无效理解
   - 标准链路应由新办理人继续
3. `unclaim` 后立刻还想按“我当前手上的任务”去 `complete`
   - 通常不成立
   - 因为任务已经被放回候选池
4. 不改办理人，却频繁调用 `claim / unclaim / transfer`
   - 这会让任务轨迹变复杂，却不解决真正的流程分支问题
5. 退回、补正、驳回场景只调 `transfer`
   - 这只是换办理人，不会自动改变 BPMN 分支

### 11.7 `POST /api/v1/workflow/tasks/{id}/complete`

#### 作用

- 完成当前任务并推动流程进入下一节点。

#### 使用场景

- 审核通过
- 退回重审
- 补充材料
- 专家复核
- 流程结束

#### 什么时候不要用

- 你只是想变更当前办理人
  - 用 `claim / unclaim / delegate / resolve / transfer`
- 当前任务是委派态，且 `delegationState=PENDING`
  - 应先由受托人 `resolve`
- 你还没有明确本次处理结果对应的变量和 BPMN 分支

#### 路径参数

- `id`
  - 运行时任务 ID

#### 请求体字段

- `activityId`
  - 当前节点 ID
- `result`
  - 业务处理结果
- `comment`
  - 办理备注
- `reworkComment`
  - 退回补充说明
- `payloadRef`
  - 业务数据引用 ID
- `needExpert`
  - 是否需要专家复核
- `variables`
  - 最终写入流程实例的变量集合

#### 字段理解要点

- `result`
  - 更适合作为业务语义字段
  - 例如：`APPROVED`、`REWORK`、`REJECTED`
- `variables`
  - 才是 BPMN 条件表达式最终真正读取的变量来源
  - 如果你的 BPMN 判断条件写的是 `${result == 'REWORK'}`，那就必须确保流程变量里的 `result` 最终值正确
- `comment / reworkComment`
  - 主要用于业务意见表达
  - 不要误以为仅靠备注文本就能决定 BPMN 分支
- `activityId`
  - 推荐显式传，尤其是一个页面支持多种处理动作时
  - 方便业务侧校验“当前页面处理的是否还是这个节点”

#### 请求体示例

```json
{
  "activityId": "task_review",
  "result": "REWORK",
  "comment": "退回申请人补充资料",
  "reworkComment": "缺少关键附件",
  "payloadRef": "BIZ-20260610-0001",
  "needExpert": false,
  "variables": {
    "result": "REWORK",
    "nextCandidateGroups": [
      "role_REVIEW_GROUP"
    ]
  }
}
```

#### 边界说明

- `complete` 才会推动 BPMN
- 已委派且 `delegationState=PENDING` 的任务不能直接 `complete`
- 退回、驳回、重审都通过变量和 BPMN 条件表达完成

#### 最容易配错的 5 个点

1. 只传顶层 `result`，却没有把 BPMN 真正依赖的变量写进 `variables`
   - 这样业务页面看起来选了“退回”，流程却可能不按预期分支走
2. 以为 `comment`、`reworkComment` 本身可以决定流程流向
   - 不对
   - 决定流向的是 BPMN 条件表达式读取到的变量
3. 已委派任务还在 `PENDING`，受托人就直接点完成
   - 标准链路不成立
   - 应先 `resolve`
4. 把“转办给别人继续处理”错误实现成当前人直接 `complete`
   - 这样推进了流程，但没有保留正确的办理权流转语义
5. 页面提交什么都往 `variables` 塞，但没有梳理流程变量契约
   - 后面排查 BPMN 分支问题会非常困难

#### 一个标准判断口诀

- 改“谁来办”：看 `claim / unclaim / delegate / resolve / transfer`
- 改“流程往哪走”：看 `complete`

#### 请求示例

```bash
curl -X POST http://127.0.0.1:9080/api/v1/workflow/tasks/<taskId>/complete \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{
    "activityId":"task_review",
    "result":"REWORK",
    "comment":"退回申请人补充资料",
    "variables":{"result":"REWORK"}
  }'
```

#### 返回示例

```json
{
  "data": {
    "taskId": "task-001",
    "status": "completed"
  },
  "message": "success"
}
```

## 12. 进度与动作时间线接口

### 12.0 前端选型口诀

- 要看“流程结构、流程图高亮、当前节点总览”，用 `progress-view`。
- 要看“用户真正能读懂的流程步骤主链路”，用 `progress-timeline`。
- 要看“某个步骤下到底发生了哪些办理动作”，用 `task-records`。
- 要看“谁把任务交给了谁”的办理权变化审计，用 `action-timeline`。
- 不要把 `progress-view.steps[]` 直接当主步骤列表。
- 不要把 `action-timeline` 直接当审批进度主列表。
- 不要只靠 `task-records` 自己拼整条主链路顺序。

### 12.1 `GET /api/v1/workflow/process-instances/{id}/progress-view`

#### 先记住这 4 条

- `progress-view` 是“结构视图接口”，不是“审批进度主列表接口”。
- 它最适合驱动：
  - 流程图高亮
  - 顶部流程摘要
  - 按 BPMN 结构展开的步骤分析
- 并行、回退、未走到的未来节点，都可能在 `steps[]` 里出现。
- 如果前端要展示用户一眼能看懂的“流程步骤”，优先去用 `progress-timeline`。

#### 作用

- 返回流程摘要、BPMN 结构化步骤视图、当前节点总览。

#### 使用场景

- 顶部流程摘要
- 流程图高亮
- 当前节点总览
- 结构化步骤分析

#### 路径参数

- `id`
  - 流程实例 ID

#### 返回字段重点

- `summary`
  - 其中：
    - `summary.startUserId` 表示流程发起人 ID
    - `summary.startUserName` 表示流程发起人显示名
- `steps`
  - 结构顺序仍然按 BPMN 正向步骤展示，不会被并行分支的时间先后打乱
- `completedActivityIds`
- `currentActivityIds`

#### `steps[]` 字段重点

- `steps[].activityId`
  - BPMN 节点 ID
- `steps[].activityName`
  - BPMN 节点名称
- `steps[].status`
  - 当前步骤状态
- `steps[].executions`
  - 该步骤真实发生过的办理执行记录列表

#### `steps[].executions[]` 字段重点

- `taskId`
  - 该次执行对应的任务 ID
- `status`
  - 该次执行当前状态，常见值：`ACTIVE`、`COMPLETED`
- `assignee`
  - 当前或最终办理人
- `owner`
  - 任务 owner
- `candidateUsers`
  - 候选用户
- `candidateGroups`
  - 候选组
- `records`
  - 该次执行下真实发生过的办理记录

#### `steps[].executions[].records[]` 字段重点

- `actionType`
  - 办理动作类型
- `operatorUserId`
  - 动作发起人
- `fromAssignee`
  - 变更前办理人
- `toAssignee`
  - 变更后办理人
- `time`
  - 动作时间

#### 说明

- 这个接口的核心定位是“结构视图”，不是“用户最终看到的审批进度主列表”。
- `steps[]` 顺序按 BPMN 结构展开，因此可能包含：
  - 未来节点
  - 回退节点
  - 尚未走到的分支节点
- 所以前端如果要做“审批进度弹窗 / 审批进度页”，不要直接把 `steps[]` 原样当主列表渲染。
- 推荐用法：
  - 用 `summary` 做顶部摘要
  - 用 `completedActivityIds/currentActivityIds` 做流程图高亮
  - 如果要做“结构分析页”，再使用 `steps[]`

#### 前端推荐用法

- 流程详情页顶部摘要
  - 用 `summary`
- 流程图高亮
  - 用 `completedActivityIds`、`currentActivityIds`
- 开发或管理员查看流程结构
  - 用 `steps[]`

#### 不要这样用

- 不要把 `steps[]` 直接渲染成用户可读的“审批步骤主列表”。
- 不要因为它字段更全，就跳过 `progress-timeline`。
- 尤其在并行分支、驳回重提、回退再走的流程里，直接平铺 `steps[]` 很容易让页面看起来重复、跳跃、难理解。

#### 请求示例

```bash
curl -H "Authorization: Bearer <token>" \
  http://127.0.0.1:9080/api/v1/workflow/process-instances/process-001/progress-view
```

### 12.2 `GET /api/v1/workflow/process-instances/{id}/progress-timeline`

#### 先记住这 5 条

- `progress-timeline` 是“流程步骤主链路接口”。
- 它回答的是：
  - “这条流程实际走到了哪些环节，现在卡在哪个环节”
- 页面上给业务人员、审批人、客户看的“流程步骤”，优先应该基于这个接口。
- 并行流程下，它负责表达“实际走过 / 当前处理中的节点链路”，而不是把整张 BPMN 结构原样摊开。
- 如果某个步骤里还要展示“认领、委派、转办、解决委派、完成”等补充动作，再结合 `task-records`。

#### 作用

- 返回流程真正走过或当前正在处理的节点推进主链路。

#### 使用场景

- 审批进度弹窗
- 业务详情页的“流程步骤”
- 用户希望看懂 `A -> B -> C` 实际流转主线

#### 路径参数

- `id`
  - 流程实例 ID

#### 返回字段重点

- `summary`
- `summary.startUserId`
- `summary.startUserName`
- `items[].itemType`
- `items[].status`
- `items[].sequence`
- `items[].occurrence`
- `items[].activityId`
- `items[].activityName`
- `items[].assignee`
- `items[].candidateUsers`
- `items[].candidateGroups`
- `items[].startTime`
- `items[].endTime`

#### 说明

- 这是前端“流程步骤主列表”推荐优先使用的接口。
- `items[]` 只返回：
  - 已经真实发生过的步骤
  - 当前正在处理的步骤
- 不会像 `progress-view.steps[]` 一样把整张 BPMN 的未来节点都平铺出来。
- 如果前端需要进一步展示：
  - “谁转办给了谁”
  - “谁委派给了谁”
  - “这一环节的意见是什么”
  则应继续结合 `task-records`，而不是直接改用 `action-timeline` 代替主列表。

#### 前端推荐用法

- 业务详情页里的“流程步骤”
  - 主列表直接使用本接口
- 我的申请详情页里的“当前流程进度”
  - 主列表直接使用本接口
- 审批弹窗里的步骤链路
  - 主列表直接使用本接口

#### 推荐组合

- 顶部摘要
  - `progress-view.summary`
- 主步骤链路
  - `progress-timeline.items[]`
- 每个步骤下的补充动作
  - `task-records.items[]`

#### 不要这样用

- 不要因为想展示转办/委派，就把主列表从 `progress-timeline` 改成 `action-timeline`。
- 不要把 `progress-timeline` 和 `action-timeline` 两份顶层列表并排直接堆到页面上，否则大多数页面会显得重复且难读。

#### 请求示例

```bash
curl -H "Authorization: Bearer <token>" \
  http://127.0.0.1:9080/api/v1/workflow/process-instances/process-001/progress-timeline
```

### 12.3 `GET /api/v1/workflow/process-instances/{id}/action-timeline`

#### 先记住这 4 条

- `action-timeline` 是“办理权变化审计接口”。
- 它最适合回答：
  - “谁认领了任务”
  - “谁委派给了谁”
  - “谁转办给了谁”
  - “委派后来是否被解决”
- 它不是主步骤接口，也不负责表达完整 BPMN 节点推进顺序。
- 如果页面主目标是“让普通用户看懂流程走到哪一步”，不要优先使用它。

#### 作用

- 返回任务办理权动作时间线。

#### 使用场景

- 展示认领、委派、转办、解决委派轨迹
- 单独补足“谁来办”的历史
- 审计排查

#### 路径参数

- `id`
  - 流程实例 ID

#### 返回字段重点

- `summary`
- `items[].actionType`
- `items[].operatorUserId`
- `items[].operatorUserName`
- `items[].fromAssignee`
- `items[].toAssignee`
- `items[].fromOwner`
- `items[].toOwner`
- `items[].reason`
- `items[].time`

#### 请求示例

```bash
curl -H "Authorization: Bearer <token>" \
  http://127.0.0.1:9080/api/v1/workflow/process-instances/process-001/action-timeline
```

#### 说明

- 这个接口现在仍然保留，但推荐定位是“动作审计辅助接口”。
- 它不负责表达完整 BPMN 节点推进顺序。
- 前端如果直接把它拿来做“审批进度主列表”，通常会出现两个问题：
  - 用户看不出主步骤顺序
  - 节点推进和办理权变化混在一起，容易重复、难读
- 推荐：
  - 主链路看 `progress-timeline`
  - 节点补充动作看 `task-records`
  - 仅在需要单独审计“谁把任务交给了谁”时，再额外展示 `action-timeline`

#### 前端推荐用法

- 审计排查页
  - 单独展示本接口
- 管理员查看某条流程的办理权变化
  - 单独展示本接口
- 业务详情页里做“展开查看办理权变化”
  - 作为补充信息展示

#### 不要这样用

- 不要把本接口单独作为“审批步骤”主列表。
- 不要把本接口的时间顺序，误认为 BPMN 结构顺序。
- 并行流程下，动作发生时间先后与节点结构顺序不是同一个概念。

### 12.7 `GET /api/v1/workflow/process-instances/{id}/task-records`

#### 先记住这 5 条

- `task-records` 是“步骤补充记录接口”。
- 它回答的是：
  - “某条流程里，各个任务实际上发生了哪些动作”
- 它可以补足：
  - 发起
  - 认领
  - 取消认领
  - 委派
  - 解决委派
  - 转办
  - 完成
- 它很适合挂到 `progress-timeline` 的每个步骤下面，做“谁转给了谁、谁处理完成”的补充文案。
- 但它本身不负责决定主步骤顺序。

#### 作用

- 按流程实例查询该流程完整的办理记录列表。

#### 使用场景

- 审计一条流程里到底谁认领、谁转办、谁完成过
- 给 `progress-timeline` 的每个步骤补充动作细节
- 排查为什么某一环节最后到了某个人手里

#### 路径参数

- `id`
  - 流程实例 ID

#### 返回字段重点

- `summary`
- `items[].actionType`
- `items[].time`
- `items[].taskId`
- `items[].activityId`
- `items[].operatorUserId`
- `items[].fromAssignee`
- `items[].toAssignee`

#### 说明

- 这个接口不是“主步骤接口”，而是“步骤补充记录接口”。
- 推荐搭配方式：
  - `progress-timeline` 决定主列表顺序
  - `task-records` 决定该步骤下展示哪些动作细节
- 常见动作类型：
  - `START_PROCESS`
  - `CLAIM`
  - `UNCLAIM`
  - `DELEGATE`
  - `RESOLVE`
  - `TRANSFER`
  - `COMPLETE`
- 前端展示时建议注意：
  - `START_PROCESS` 通常不要再重复挂到第一个步骤下面，否则容易出现“两个发起流程”的重复展示
  - `TRANSFER / DELEGATE / RESOLVE / CLAIM / UNCLAIM` 更适合作为步骤下的“流转补充文案”
  - `COMPLETE` 更适合作为“办理意见 / 已处理完成”来源之一

#### 前端推荐用法

- 审批进度页
  - 用它补充每个步骤下的动作明细
- 办理轨迹页
  - 可直接按时间展示完整动作列表
- 结合 `activityId + taskId`
  - 精细挂载到对应步骤或执行记录下

#### 不要这样用

- 不要只依赖本接口就直接画整条“流程步骤”。
- 不要把 `START_PROCESS` 和第一步节点再重复展示两次“发起流程”。
- 不要忽略 `activityId / taskId / time / actionType` 这些字段的组合关系，前端挂载时应该按步骤归组，而不是简单全文字平铺。

#### 请求示例

```bash
curl -H "Authorization: Bearer <token>" \
  http://127.0.0.1:9080/api/v1/workflow/process-instances/process-001/task-records
```

## 14. 回调接口

### 14.1 3 分钟看懂：`POST /api/v1/workflow/callback`

这一节已经整合了《Flowable Callback 接口 3 分钟速读版》的核心内容。
如果你现在只想快速弄明白这个接口怎么配、谁来调、收到后做什么，直接看完这一节即可。

#### Q0. 先只记住这 7 条

如果你时间很少，先记住下面 7 条，基本就不会把 callback 接错：

1. `/api/v1/workflow/callback` 不是前端页面调用的接口
   - 正常调用方是 Flowable
2. 业务系统必须先注册：
   - `workflowapi.MustRegisterFromConfig(server)`
   - 否则这个路由根本不会真正对外提供
3. `workflow.callback.path`
   - 只决定“业务系统把 callback 路由暴露在哪个路径”
   - 它不是完整 callback 地址
4. `workflow.callback.public_base_url`
   - 只决定“Flowable 从外部访问业务系统时，应该打哪个宿主地址”
   - 它不能写成 Flowable 自己访问不到的 `localhost`
5. 真正让 Flowable 产生回调的关键，不是只配 YAML，而是启动流程时明确传：
   - `variables.callbackUrl`
   - `variables.callbackEvents`
6. 当前 go-common 标准 callback 收到事件后：
   - 会刷新待办、已办、流程摘要、步骤、记录这些工作流侧读模型
   - 不会自动修改你的业务主表状态
7. 如果你希望“节点处理完成后更新业务表字段”
   - 要在业务系统自己的 callback 扩展层里实现
   - 不要误以为平台已经默认帮你做了

#### Q1. 我需要前端调用这个接口吗？

不需要。

直接结论：

1. `POST /api/v1/workflow/callback` 不是前端调的。
2. 它也不是业务页面按钮直接调的。
3. 它通常是 Flowable 在流程运行过程中自动回调到业务系统的一个内部接口。
4. 你要让它生效，关键不是“手动调这个接口”，而是“启动流程时把 `callbackUrl` 和 `callbackEvents` 传给 Flowable”。
5. 当前 `go-common` 标准实现收到回调后，只会刷新工作流侧读模型，不会自动更新你的业务主表。
6. 如果你想在“节点完成后同步改业务表状态”，要基于这个回调事件做业务扩展处理。

#### Q2. 那到底是谁来调用它？

- 正常调用方：Flowable
- 非正常调用方：前端页面、业务按钮、人工日常操作

补一句：

- 你当然可以在联调时手工 `curl` 这个接口做验签或报文调试
- 但那只是调试手段，不是正常业务链路
- 真正上线后的标准调用方仍然应该是 Flowable

也就是说，正常链路是：

1. 业务系统调用 `POST /api/v1/workflow/process/start`
2. 请求里通过 `variables.callbackUrl` 告诉 Flowable：“后面事件发生时，请回调这个地址”
3. Flowable 在流程运行过程中，自动 `POST /api/v1/workflow/callback`
4. `go-common` 收到后刷新待办、已办、流程摘要等工作流侧数据

#### Q3. 它什么时候会被调用？

最常见是 4 类事件：

- `PROCESS_STARTED`
  - 流程刚启动
- `NODE_STARTED`
  - 某个节点刚进入运行态
- `NODE_ENDED`
  - 某个节点刚处理完成
- `PROCESS_ENDED`
  - 整个流程结束

如果你在启动流程时没有传 `callbackUrl` 或没有声明 `callbackEvents`，那就不会有这类自动回调。

#### Q4. 我真正应该怎么接这个接口？

真正的使用方式不是“去写一个页面点这个接口”，而是下面这条链路：

第 1 步，启动流程时配置回调地址和事件：

```json
{
  "processDefinitionKey": "asset_approval_process",
  "bizId": "BIZ-20260610-0001",
  "bizType": "asset_approval",
  "title": "资产审批申请示例",
  "variables": {
    "callbackUrl": "http://127.0.0.1:9080/api/v1/workflow/callback",
    "callbackEvents": "PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED"
  }
}
```

第 2 步，Flowable 在事件发生时自动回调：

```http
POST /api/v1/workflow/callback
Content-Type: application/json
```

```json
{
  "eventId": "evt-001",
  "eventType": "NODE_ENDED",
  "eventTime": "2026-06-10T10:00:00+08:00",
  "processInstanceId": "process-001",
  "processDefinitionId": "asset_approval_process:3:abc",
  "activityId": "task_review",
  "taskId": "task-001",
  "bizId": "BIZ-20260610-0001",
  "variables": {
    "bizType": "asset_approval",
    "title": "资产审批申请示例",
    "result": "APPROVED"
  }
}
```

第 3 步，`go-common` 返回成功：

```json
{
  "data": {
    "accepted": true
  },
  "message": "success"
}
```

这就是 `api/v1/workflow/callback` 的标准使用方式。

#### Q4.0 用一句话说完 callback 的最小闭环

最小闭环只有 5 步：

1. 业务系统启动时注册 `workflowapi.MustRegisterFromConfig(server)`
2. `config.yaml` 里把 `workflow.callback.path` 配成 `/api/v1/workflow/callback`
3. `config.yaml` 里把 `workflow.callback.public_base_url` 配成 Flowable 可访问地址
4. 启动流程时传：
   - `variables.callbackUrl`
   - `variables.callbackEvents`
5. 业务系统在 callback 扩展处理中，按需要更新自己的业务表状态

如果这 5 步里少任何一步，callback 都不会形成真正可用闭环。

#### Q4.1 后端代码里到底怎么把 callback 接起来？

很多开发看完接口说明后，还是不知道“代码里我到底要写什么”。这里直接给最小结论：

1. 你**不用手写** `POST /api/v1/workflow/callback` 这个路由。
2. 你只需要在业务系统启动时注册：

```go
workflowapi.MustRegisterFromConfig(server)
```

3. 然后在 `config.yaml` 里把 callback 路径和密钥配置好。
4. 最后在“启动流程”请求里传入 `variables.callbackUrl` 和 `variables.callbackEvents`。

也就是说，代码接入分成两部分：

- 第一部分：业务系统启动时，把 go-common 的工作流模块注册进来
- 第二部分：业务系统发起流程时，把 callback 参数传给 Flowable

最小后端启动示例：

```go
package main

import (
    commonhttp "github.com/goodbye-jack/go-common/http"
    workflowapi "github.com/goodbye-jack/go-common/workflow/api"
)

func main() {
    server := commonhttp.NewHTTPServer("demo-service")

    // 先注册你自己的业务接口
    registerBizRoutes(server)

    // 再注册 go-common 标准工作流接口
    // 这里会自动注册：
    // 1. /api/v1/workflow/... 标准接口
    // 2. /api/v1/workflow/callback 回调接口
    workflowapi.MustRegisterFromConfig(server)

    server.Prepare()
    server.Run(":9080")
}
```

这段代码的含义要理解清楚：

- `registerBizRoutes(server)`
  - 注册你自己的业务保存、业务详情、业务列表等接口
- `workflowapi.MustRegisterFromConfig(server)`
  - 自动注册 go-common 提供的标准工作流接口
  - 自动注册 `workflow.callback.path` 对应的 callback 路由
  - 自动按 `workflow.callback.secret` 决定是否验签
- `server.Prepare()`
  - 让所有路由和鉴权元数据正式生效

如果你没有调用 `workflowapi.MustRegisterFromConfig(server)`，那就算 YAML 配了 callback，也不会真正对外提供这个接口。

#### Q4.2 `config.yaml` 里 callback 相关配置怎么写？

最小推荐配置如下：

```yaml
workflow:
  api:
    enabled: true
    prefix: "/api/v1/workflow"
  callback:
    path: "/api/v1/workflow/callback"
    secret: ""
    public_base_url: "http://127.0.0.1:9080"
  flowable:
    base_url: "http://127.0.0.1:8087/flowable-rest/service"
    username: "rest-admin"
    password: "PLEASE_CHANGE"
```

字段含义：

- `workflow.api.enabled`
  - 是否启用 go-common 工作流标准接口
- `workflow.api.prefix`
  - 标准工作流接口前缀
  - 例如：`/api/v1/workflow`
- `workflow.callback.path`
  - callback 接口在业务系统中的暴露路径
  - 推荐固定为：`/api/v1/workflow/callback`
- `workflow.callback.secret`
  - callback 验签密钥
  - 为空表示不验签
  - 非空表示 Flowable 或中间适配层调用 callback 时必须带签名头
- `workflow.callback.public_base_url`
  - Flowable 运行时访问业务系统 callback 的外部基地址
  - 启动流程时构造 `callbackUrl` 必须优先使用这个值
  - 如果是远端 Flowable 联调，这里必须写 Flowable 可访问到的地址
- `workflow.flowable.base_url`
  - go-common 调用 Flowable REST 的地址

一条原则：

- `workflow.callback.path` 决定“业务系统把回调接口暴露在哪”
- `callbackUrl` 决定“Flowable 运行时回调到哪个完整地址”

前者是**本地服务注册路径**，后者是**启动流程时传给 Flowable 的完整 URL**，两者不要混淆。

建议直接按下面 2 种场景去理解，不要自己脑补第三种语义：

场景 1：本地 Flowable + 本地业务系统

- `workflow.flowable.base_url`
  - 可写本机 Flowable REST 地址
  - 例如：`http://127.0.0.1:8087/flowable-rest/service`
- `workflow.callback.public_base_url`
  - 可写本机业务系统地址
  - 例如：`http://127.0.0.1:9080`

场景 2：远端 Flowable + 本地业务系统联调

- `workflow.flowable.base_url`
  - 写远端 Flowable REST 地址
  - 例如：`http://124.222.38.121:9090/flowable-rest/service`
- `workflow.callback.public_base_url`
  - 不能写 `http://127.0.0.1:9080`
  - 必须写远端 Flowable 真正能访问到的地址
  - 例如：公网网关地址、反向代理地址、FRP 地址

如果你把这两个地址都写成同一个值，只有在“Flowable 和业务系统本来就在同一宿主可互通环境里”才可能是对的。
一旦是远端联调，这两个值大概率就不应该一样。

再说得更直白一点：

1. 你只配 `workflow.callback.path`
   - 业务系统只是“把门开好了”
2. 你还要配 `workflow.callback.public_base_url`
   - 业务系统才知道应该把哪一个外部可达地址告诉 Flowable
3. 你再在启动流程时传 `variables.callbackUrl`
   - 才是“告诉 Flowable 回调到哪扇门”

所以“业务系统明明已经有 `/api/v1/workflow/callback` 路由了，但为什么一直收不到回调”，最常见根因不是路由没注册，而是下面 3 种：

1. 启动流程时没传 `callbackUrl`
2. 启动流程时没传 `callbackEvents`
3. `callbackUrl` 虽然传了，但 Flowable 所在环境根本访问不到这个地址

再补一个容易让开发误会的点：

- `workflow.callback.secret`
  - 是**接收端验签配置**
  - 不是“自动帮你生成 callback 签名”的开关
  - 也不是“自动把 callbackUrl 注入流程变量”的配置
- `workflow.callback.public_base_url`
  - 为空时不应该再自动回退到 `localhost`、`127.0.0.1` 或监听地址去伪造 callback 地址
  - 要么显式配置，要么由业务代码显式传入 `variables.callbackUrl`

#### Q4.3 发起流程时，业务代码怎么把 callback 信息传进去？

callback 不是单靠注册路由就会自动触发，发起流程时还必须在启动请求里明确传入：

- `variables.callbackUrl`
- `variables.callbackEvents`

如果你的业务程序已经把 go-common 工作流接口注册到了：

- `workflow.api.prefix: "/api/v1/workflow"`
- `workflow.callback.path: "/api/v1/workflow/callback"`
- `workflow.callback.public_base_url: "http://your-biz-host:9080"`

那么业务代码真正需要做的只是两件事：

1. 启动流程时把 `callbackUrl` 传成“当前业务系统自己可被 Flowable 访问到的完整地址”
   - 例如：`http://your-biz-host:9080/api/v1/workflow/callback`
2. 选择要订阅的回调事件
   - 例如：`PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED`

也就是说：

- `go-common` 负责“把接收 callback 的接口暴露出来并处理它”
- 业务系统负责“在启动流程时把 callback 地址和事件订阅告诉 Flowable”

标准做法示例：

```go
startReq := map[string]interface{}{
    "processDefinitionKey": "generic_approval_demo",
    "bizId":                bizID,
    "bizType":              "generic_approval",
    "title":                title,
    "name":                 title,
    "variables": map[string]interface{}{
        "starterId":      currentUserID,
        "starterName":    currentUserName,
        "callbackUrl":    "http://127.0.0.1:9080/api/v1/workflow/callback",
        "callbackEvents": "PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED",
    },
}
```

如果你的业务系统对外地址来自配置，推荐这样拼：

```go
callbackURL := strings.TrimRight(baseURL, "/") + "/api/v1/workflow/callback"
```

更推荐直接按配置语义拼，而不是手写常量：

```go
callbackURL := strings.TrimRight(callbackPublicBaseURL, "/") + callbackPath
```

这里的 `callbackPublicBaseURL` 应对应：

- `workflow.callback.public_base_url`

这里的 `callbackPath` 应对应：

- `workflow.callback.path`

这里建议业务代码按“强约束”方式实现，而不是“缺了先凑合跑”：

1. `workflow.callback.path` 没配
   - 就在构造启动请求前直接报错
   - 不要再偷偷回退到 `/api/v1/workflow/callback`
2. `workflow.callback.public_base_url` 没配
   - 也应直接报错
   - 不要自动回退到 `localhost`、`127.0.0.1`、`server.addr` 或监听端口
3. 只有 `MustRegisterFromConfig(server)` 注册了 callback 路由，但启动流程时没传 `callbackUrl / callbackEvents`
   - 也不会产生任何 Flowable 回调
   - 这一点最容易被误解成“明明 callback 接口已经有了，为什么还是没收到回调”

当前公司标准建议是：

- `workflow.callback.path`
  - 在 `config.yaml` 中显式声明
- `workflow.callback.public_base_url`
  - 在 `config.yaml` 或业务系统自己的启动环境变量中显式提供
- 业务系统启动流程封装器
  - 对这两个值缺失都直接失败

这样做的目的不是“更严格”，而是避免把配置错误拖到联调阶段才暴露。

再补一个很实用的落地建议：

- 不要让每个业务模块自己拼 `callbackUrl`
- 应该由业务系统统一封装一个“启动流程请求构造器”
- 由这一个构造器统一完成：
  - 读取 `workflow.callback.path`
  - 读取 `workflow.callback.public_base_url`
  - 生成 `variables.callbackUrl`
  - 生成 `variables.callbackEvents`
  - 对缺失配置直接报错

这样后面就不会出现：

- A 模块传了 callback
- B 模块没传 callback
- C 模块路径写成旧值
- D 模块直接把 `localhost` 传给远端 Flowable

#### Q4.4 开发人员真正需要自己写的业务代码是什么？

`go-common` 已经帮你做好的部分：

- 暴露 `POST /api/v1/workflow/callback`
- 验签
- 解析回调 JSON
- 刷新工作流读模型
  - 待办
  - 已办
  - 流程摘要
  - 流程步骤
  - 办理记录

开发人员仍然需要自己实现的部分：

- 业务保存接口
- 业务详情接口
- 启动流程前的业务数据落库
- 如果有需要，基于 callback 事件去更新业务主表状态
- 如果有需要，基于 callback 事件写业务审核日志、通知、归档等逻辑

换句话说：

- `go-common` 负责“工作流标准能力”
- 业务系统负责“你的业务字段怎么变化”

这里给一个最常见的业务扩展例子：

- 收到 `PROCESS_STARTED`
  - 业务主表状态可改成“审批中”
- 收到 `NODE_ENDED`
  - 可按 `activityId + result` 更新当前业务审核状态
- 收到 `PROCESS_ENDED`
  - 可把业务主表状态改成“已完成 / 已驳回 / 已终止”

也就是说：

- callback 支持你在节点处理完成后更新业务系统表字段状态
- 但“更新成什么、怎么更新、更新哪张表”必须由业务系统自己实现

#### Q4.5 当前 callback 标准能力不负责什么？

这一点一定要写清楚，避免开发误解：

当前 `go-common` 标准 callback 能力**不会自动**帮你做下面这些事：

- 不会自动把 `processInstanceId` 回写进你的业务主表
- 不会自动把业务状态从“草稿”改成“审批中”
- 不会自动把节点结果写进你的业务审核表
- 不会自动发短信、发站内信、发邮件
- 不会自动执行你的行业特有补偿逻辑

也就是说，如果你们项目希望：

- 节点结束后自动更新业务状态
- 流程结束后自动把业务单据改成“已完成”
- 自动记录业务审计日志

这些都要由业务系统自己补业务代码，不要误以为 callback 已经默认帮你做完。

#### Q4.6 callback 的标准职责到底分几层？

当前标准 callback 建议按两层理解：

第 1 层：`go-common` 标准能力

- 接收 `POST /api/v1/workflow/callback`
- 按 `workflow.callback.secret` 决定是否验签
- 解析 callback JSON
- 刷新工作流侧读模型
  - 待办
  - 已办
  - 流程摘要
  - 流程步骤
  - 办理记录

第 2 层：业务系统扩展能力

- 根据 `bizId / payloadRef` 找到业务主表
- 更新业务状态
- 记录业务审核日志
- 做通知、归档、统计等业务扩展

一句话：

- `go-common` 负责“工作流事件到了，并把工作流侧数据刷对”
- 业务系统负责“我的业务字段应该怎么变”

#### Q4.7 callback 日志里至少应该看到什么？

为了后续联调和排查，建议标准 callback 日志至少包含下面这些字段：

- `eventType`
- `eventId`
- `bizId`
- `payloadRef`
- `processInstanceId`
- `processDefinitionId`
- `taskId`
- `activityId`
- `eventTime`
- `signatureVerified`
- `projectionResult`
- `businessHandlerResult`

如果缺少这些字段，后面排查“到底哪个业务单号回调了、哪个节点结束了、业务状态为什么没更新”会非常困难。

#### Q5. 启动流程时到底要传什么？

你真正需要关心的是启动流程时下面两个变量：

- `callbackUrl`
  - 含义：Flowable 以后要把事件回调到哪个地址
  - 示例：`http://127.0.0.1:9080/api/v1/workflow/callback`
- `callbackEvents`
  - 含义：哪些事件发生时要回调
  - 示例：`PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED`

最推荐的启动示例：

```json
{
  "processDefinitionKey": "asset_approval_process",
  "bizId": "BIZ-20260610-0001",
  "bizType": "asset_approval",
  "title": "资产审批申请示例",
  "name": "资产审批申请示例",
  "variables": {
    "starterId": "test1",
    "starterName": "测试用户1",
    "callbackUrl": "http://127.0.0.1:9080/api/v1/workflow/callback",
    "callbackEvents": "PROCESS_STARTED,NODE_STARTED,NODE_ENDED,PROCESS_ENDED"
  }
}
```

如果你现在问“我到底该不该配回调”，可以直接这样判断：

- 只想用待办、已办、流程进度，并希望这些信息实时刷新：建议配
- 还想在节点完成后联动更新业务表状态：必须配
- 只是做极简演示，不关心回调和状态同步：可以先不配

#### Q6. 为什么我没有收到回调？

先按下面顺序排查：

1. 启动流程时有没有传 `variables.callbackUrl`
2. 启动流程时有没有传 `variables.callbackEvents`
3. `callbackUrl` 地址是否能被 Flowable 所在环境访问到
4. 你订阅的事件里是否包含当前发生的事件
5. 如果配置了 `workflow.callback.secret`，调用方是否按要求带了签名头

最常见的原因就两个：

- 根本没配 `callbackUrl / callbackEvents`
- 地址配置了，但 Flowable 根本打不到这个地址

再补 2 个实际联调里很常见的原因：

- 业务系统虽然暴露了 `/api/v1/workflow/callback`，但实际对外地址写成了本机回环地址，Flowable 所在服务器无法访问
- 配了 `workflow.callback.secret`，但调用方没有按要求带签名头，结果被业务系统直接拒绝

如果你不想每次都靠猜，建议直接按下面顺序排：

1. 看业务系统启动日志
   - 是否已经注册了 `/api/v1/workflow/callback`
   - 是否打印了 `callback_route=...`
2. 看启动流程请求体
   - 是否真的带了 `variables.callbackUrl`
   - 是否真的带了 `variables.callbackEvents`
3. 看 `callbackUrl` 的宿主地址
   - 如果 Flowable 在远端，而这里是 `127.0.0.1` / `localhost`，基本就已经错了
4. 看 Flowable 所在环境能不能访问这个 `callbackUrl`
   - 这是远端联调时最常见的根因
5. 看业务系统 callback 日志
   - 如果完全没有收到请求，问题通常在“地址不可达”或“启动流程时没传 callback 变量”
   - 如果收到了但返回 401，问题通常在验签
   - 如果收到了但业务表没变化，问题通常在“你没有写业务扩展处理”

可以直接把排错结果归类成 3 种：

1. 根本没打到 callback 路由
   - 常见原因：没注册路由、没传 callback 变量、地址不可达
2. 打到了 callback 路由，但标准 callback 返回 401 / 4xx
   - 常见原因：验签头缺失或签名错误
3. 打到了 callback 路由，也返回成功了，但业务状态没变
   - 常见原因：你还没有补业务系统自己的 callback 扩展处理

#### Q7. 请求头要不要签名？

默认情况下：

- `Content-Type: application/json`

如果你配置了 `workflow.callback.secret`，还必须带下面 3 个头：

- `X-Timestamp`
  - 当前时间戳
- `X-Nonce`
  - 随机串
- `X-Signature`
  - 签名结果

签名规则是：

```text
timestamp + "\n" + nonce + "\n" + body
```

签名算法是：

```text
HMAC-SHA256
```

也就是说：

- 没配 `workflow.callback.secret`
  - 不验签
- 配了 `workflow.callback.secret`
  - 少任何一个签名头都会返回 `401 Unauthorized`

#### Q8. 请求体每个字段到底是什么意思？

- `eventId`
  - 本次回调事件 ID
  - 建议业务扩展侧拿它做幂等去重
- `eventType`
  - 本次事件类型
  - 最常见就是 `PROCESS_STARTED`、`NODE_STARTED`、`NODE_ENDED`、`PROCESS_ENDED`
- `eventTime`
  - 本次事件发生时间
- `processInstanceId`
  - 流程实例 ID
  - 查流程进度、查流程图、更新业务流程状态时很常用
- `processDefinitionId`
  - 流程定义 ID
  - 主要用于调试、区分具体部署版本
- `activityId`
  - 当前节点 ID
  - 例如：`task_review`
  - 业务扩展时经常用它判断“是哪个节点结束了”
- `taskId`
  - 当前任务 ID
  - 对任务级事件最有用
- `bizId`
  - 你的业务主键
  - 回写业务表最关键的关联字段之一
- `variables`
  - 当时的流程变量快照
  - 里面通常会带标题、结果、发起人、下一节点变量等

#### Q9. 返回 `accepted=true` 到底代表什么？

返回示例：

```json
{
  "data": {
    "accepted": true
  },
  "message": "success"
}
```

字段含义：

- `accepted=true`
  - 表示这个回调请求已经被当前标准处理链路接收
  - 包含：验签通过、JSON 解析通过、标准回调处理通过

但这里一定不要过度解读：

- `accepted=true`
  - 不等于“你的业务主表已经更新成功”
  - 不等于“你的通知、归档、审计日志都已经执行成功”
  - 它只代表 go-common 这一层标准 callback 处理已经接收并完成自己的标准动作

所以如果你们项目做了业务扩展层，建议你们自己额外在业务日志里明确打印：

- 业务扩展是否执行
- 命中了哪个业务单
- 更新了哪张表
- 更新结果是否成功

这个返回值的重点不是给前端展示，而是告诉回调方：“这条事件我收到了”。

#### Q10. 当前 `go-common` 收到回调后到底做了什么？

当前标准实现只做工作流平台侧的同步：

- `PROCESS_STARTED`
  - 刷新流程摘要
- `NODE_STARTED`
  - 同步运行中待办
  - 刷新流程摘要
- `NODE_ENDED`
  - 同步已办
  - 删除运行中待办
  - 刷新流程摘要
- `PROCESS_ENDED`
  - 清理流程实例下的运行中待办
  - 刷新流程摘要

一句话：

- 它主要解决“待办、已办、流程进度要及时更新”
- 它默认不替你猜业务主表应该怎么变

#### Q11. 为什么回调成功了，但业务表状态没变？

当前标准实现不会自动帮你做下面这些业务动作：

- 不会自动更新业务主表状态
- 不会自动更新业务审核字段
- 不会自动插入业务审核日志
- 不会自动发短信、发站内信、发邮件
- 不会自动做你的行业逻辑补偿

因为当前标准实现不会自动改你的业务主表。

所以千万不要误解成：

- “我把 `callbackUrl` 配上，业务表状态就会自动变”

当前标准实现不是这个语义。

#### Q12. 那它支不支持“节点完成后更新业务表字段”？

支持，但这是“基于回调事件做业务扩展”，不是“平台已经默认帮你写好”。

最典型的扩展方式如下：

- 收到 `PROCESS_STARTED`
  - 把 `processInstanceId` 回写到你的业务主表
  - 记录 `workflow_started_at`
- 收到 `NODE_STARTED`
  - 更新当前处理节点编码
  - 更新当前处理节点名称
- 收到 `NODE_ENDED`
  - 更新本节点处理结果
  - 记录最近处理时间
  - 追加业务审核日志
- 收到 `PROCESS_ENDED`
  - 更新业务流程总状态
  - 记录流程完成时间

#### Q13. 我应该在哪一层写业务状态更新？

应该写在业务系统自己的事件处理层，不应该误以为写在前端，也不应该误以为 `go-common` 默认已经帮你写好了。

推荐分层：

1. `go-common` 标准回调接收层
   - 负责验签
   - 负责解析回调请求
   - 负责刷新工作流侧读模型
2. 业务系统事件处理层
   - 负责更新业务主表
   - 负责写业务日志
   - 负责通知、归档、统计等扩展逻辑

一句话：

- 工作流平台负责“事件到了”
- 业务系统负责“业务字段怎么变”

推荐落点是：

- 使用 `go-common` 标准 callback 路由
- 在 callback 扩展处理层里补业务状态更新

不推荐：

- 业务系统再额外暴露一套平行 callback 路由
- 不走标准 callback 路径，自己绕开 go-common 去单独接 Flowable 事件

#### Q14. 给我一个最实际的业务扩展示例

假设你的业务表叫 `biz_order`。

收到 `NODE_ENDED` 时，可以这样理解：

```text
根据 bizId 找到业务单
根据 activityId 判断是哪一个节点完成
根据 variables.result 更新本次处理结果
根据 eventTime 更新最后处理时间
插入一条业务审核日志
```

可能对应的业务字段语义是：

- `biz_order.current_node_code = 'task_review'`
- `biz_order.current_node_status = 'DONE'`
- `biz_order.last_result = 'APPROVED'`
- `biz_order.last_operated_at = eventTime`

收到 `PROCESS_ENDED` 时，可以这样理解：

- `biz_order.workflow_status = 'COMPLETED'`
- `biz_order.completed_at = eventTime`

#### Q15. 回调重复推送怎么办？

因为回调有可能重复投递，所以建议至少这样处理：

1. 优先用 `eventId` 做幂等键
2. 如果上游没有稳定 `eventId`，就组合：
   - `processInstanceId`
   - `taskId`
   - `activityId`
   - `eventType`
   - `eventTime`
3. 业务日志表最好建唯一索引，避免重复写入

#### Q16. 联调时我能不能手工测？

正式环境不应该手工调用，但联调时可以用 `curl` 模拟一条回调：

```bash
curl -X POST http://127.0.0.1:9080/api/v1/workflow/callback \
  -H "Content-Type: application/json" \
  -d '{
    "eventId":"evt-001",
    "eventType":"NODE_ENDED",
    "eventTime":"2026-06-10T10:00:00+08:00",
    "processInstanceId":"process-001",
    "processDefinitionId":"asset_approval_process:3:abc",
    "activityId":"task_review",
    "taskId":"task-001",
    "bizId":"BIZ-20260610-0001",
    "variables":{
      "bizType":"asset_approval",
      "result":"APPROVED"
    }
  }'
```

如果配置了 `workflow.callback.secret`，还要额外补签名头，否则会直接返回 `401 Unauthorized`。

#### Q17. 最后一句话怎么记？

- `/api/v1/workflow/callback` 不是“给页面调用的业务接口”。
- 它是“Flowable 自动回调过来的内部事件接口”。
- 当前标准能力负责刷新工作流侧数据。
- 业务表要不要跟着更新，要由业务系统基于回调事件自己扩展。

## 15. 前端推荐页面结构

前端推荐至少拆成下面几类页面：

1. 发起页
2. 我的申请页
3. 我的待办页
4. 我的已办页
5. 业务详情页
6. 任务处理页
7. 流程进度页

### 15.1 处理页建议分三块

1. 业务详情
2. 任务管理动作
   - 认领
   - 释放
   - 委派
   - 转办
   - 解决委派
3. 业务处理动作
   - 通过
   - 退回
   - 驳回
   - 补正

### 15.2 时间线建议分两块

1. 主进度链路
   - `progress-timeline`
   - 用来展示真正走过或当前正在处理的步骤
2. 节点补充动作
   - `task-records`
   - 用来展示某一步里发生的转办、委派、解决委派、完成等动作
3. 动作审计页
   - `action-timeline`
   - 只在需要单独审计“办理权如何变化”时使用

### 15.3 审批进度页推荐组合

推荐组合：

1. 顶部摘要和流程图
   - `progress-view`
2. 主步骤列表
   - `progress-timeline`
3. 每个步骤下的动作补充
   - `task-records`

不要这样组合：

1. 直接把 `progress-view.steps[]` 当审批进度主列表
2. 直接把 `action-timeline` 当审批进度主列表

推荐展示逻辑：

1. 主列表一行只表示一个真实步骤
2. 该步骤的处理人、创建时间、完成时间、状态来自 `progress-timeline.items[]`
3. 该步骤下的转办 / 委派 / 解决委派 / 完成意见来自 `task-records`
4. `START_PROCESS` 不建议重复挂入第一个步骤的动作列表

前端伪代码示例：

```ts
const [progressView, progressTimeline, taskRecords] = await Promise.all([
  getBizProgressView(bizId),
  getBizProgressTimeline(bizId),
  getBizTaskRecords(bizId),
]);

const stepList = progressTimeline.items.map((step) => {
  const records = taskRecords.items.filter((record) => {
    if (record.actionType === "START_PROCESS") {
      return false;
    }
    if (step.taskId && record.taskId === step.taskId) {
      return true;
    }
    return !step.taskId && step.activityId && record.activityId === step.activityId;
  });

  return {
    step,
    records,
  };
});
```
